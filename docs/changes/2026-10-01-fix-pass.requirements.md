# Product Requirements: Fix pass

Technical part: [2026-10-01-fix-pass.design.md](2026-10-01-fix-pass.design.md).

## Summary

`deep-review review --fix` carries a review past its findings: after
merge and rank, the engine clusters the findings that route to a fixer,
gives each cluster to one fix worker that owns the cluster's files for the
pass, runs the project's own checks (build, typecheck, lint, test) once
before any edit and again after the fixers return, sends the checks that
the fixers broke to one repair worker, runs the checks once more, and
writes the report with what was applied, what was deferred or blocked,
what the checks said and what changed in the tree, beside a patch
series with one patch per finding. The tree is edited by fix workers
only, never by the engine during a run, and every edit is observed: a
fixer snapshots its files after each finding, the engine freezes the
bytes each change left, so the run keeps knowing what the tree should
hold, a change nobody accounts for still blocks it, and the patches are
rendered from those bytes, not from git. Nothing is committed by the
run; afterwards, when the user asks, `deep-review commit` turns the
series into one commit per finding with the fixer's message, from the
frozen bytes, without touching a file. Without `--fix` nothing changes:
the read-only review stays as it is.

Amended on 2026-10-02 after the first gate run (R16), on Claude Code,
reached a report but left the three best-ranked findings unfixed and
lost the per-finding record of fourteen others (Verification of the
design). A cluster's findings are now fixed in batches of at most four,
one batch after another, best-ranked first across the run (R18); in an
editing phase the run budget stops new launches instead of blocking the
run (R19); a failed attempt's edits are recorded from its snapshots when
it fails, so the retry's revisions are its own (R20); a finding blocked
only on files another cluster owned gets one second round once those
clusters have settled (R21); and a file is changed when git would store
it differently, so a line-ending conversion is not an edit (R22).

Amended again on 2026-10-03 after the gate ran on both runtimes with
the first amendment (Verification of the design). Both reached a
report, but Claude's diff broke three of zod's bundle-size ceilings,
which no check saw because `test` already failed at baseline, and on
Codex the snapshot command could not start git, since Codex's Windows
sandbox lets no process a worker starts start another. The snapshot
command now finds what changed from a manifest the engine writes at
launch and starts no process (R23); a check that failed at baseline and
still fails goes to the repair worker with both outputs, and every
fixer is told what failed before any fix (R24); the fixer's timeout is
1800 s (R25); Claude's default run budget is 60 USD (R26); and the log
names a revision of no finding as what it is (R27).

This is the sixth element of the plan, the first that edits the reviewed
tree, and the first that runs commands the repository defines. It takes
the three boundaries the pilots broke on after findings were ranked: the
engine to the fix worker (ownership, what a fixer reports, a half-applied
fix), the engine to the operating system (a check that outlives its
process, a check that writes), and the engine to the repository (which
commands are the checks, in what order).

## Problem

The read-only review delivers a report; the deep review the skill
promises applies the fixes. The proof of concept ran the whole fix loop
and never finished a pilot run; its defects after ranking are the
evidence here, from `agent-skills`
(`docs/handover/2026-09-22-deep-review-node-tarkov-pilot-defects.md`
and its follow-ups in `deep-review-node-engine-problems.md`, read at
`822986e`).

- Ownership was right in principle and a dead end in practice. One
  cluster per file, merged findings kept whole, no file in two
  concurrent clusters: the pilots never clobbered an edit. But a fixer
  could only own a test file that the change already touched and a
  layout rule classified as a test, so a fix whose test belonged in an
  untouched file could not be owned at all (the main defect of the
  engine problems, fixed there by a pinned layout, a test-ownership
  planner and an expansion budget: three mechanisms for one rule). A
  fixer blocked for a file it did not own had no path forward until a
  replan command existed.
- A tree that changed under the engine ended the run. Drift was one hash
  over the whole tree, so a stray scratch file (D3) or a sibling
  editor's legitimate edit (follow-up 5: a fixer that deferred with no
  edits was classified as drift because its siblings had edited) was
  indistinguishable from a real conflict, and the recorded hash could
  never match again.
- Checks that shared a build output ran at once: `dotnet build` and
  `dotnet test --no-build` started in the same second, the build failed
  on a locked assembly and the test "passed" on stale binaries (run
  `6b7cbf80`). The fix there was a strict chain, typecheck then lint then
  test, and a compile step had to be filed under `typecheck` because no
  `build` kind existed (D1).
- Build servers outlived the check that started them: eight MSBuild
  nodes survived a worker, the job object drained 138 descendants and
  the run was classified unrecoverable (D7). The environment pins that
  stop node reuse were found and belong in the design, not in a patch.
- A machine that slept for eleven hours with a test check running timed
  the check out on waking (`c53b38ed`); nothing recognises the case.
- The fixers' return was prose (`APPLIED`, `DEFERRED`, `BLOCKED`,
  `FILES`, `SUITE` lines) parsed by convention, and a fixer that kept a
  partial edit under `DEFERRED` crashed acceptance with a bare error
  (follow-up 4).
- The engine parsed check output to decide whether a failure was a code
  defect, with one parser per recognised tool and a blocker for every
  unrecognised format; any stderr output disabled the parsers. The
  classification was the most code on the editing path and the least
  exercised.
- On the second Tarkov session the fixes a run had produced were read by
  hand and committed as `383a579`: four of six edits were real gaps in
  the reviewed change. The fix pass finds real work; the engine around
  it did not deliver it.

In this repository the read-only review runs whole (element five, gate
passed on zod #6530 on both runtimes on 2026-09-29), the `fixer` role's
prompt is assembled from fragments here and still describes the proof
of concept's return format and a strict "edit nothing outside your
files" rule, the runtime adapter proved on both runtimes that an editor
with `edit` access writes into the repository and its scratch directory
(runtime adapter, Verification), and scope capture left a note that a
later revision of the scope would be recorded by the editing element
with the same freezing code (scope capture, Non-Goals). The read-only
element deferred to this one: editing, the fixer, the documentation
pass, the test assessment and check execution (its Non-Goals); the
"held for the author" routing of `PLAUSIBLE` design findings; and the
`Step 1` and `Step 3` names it removed from `rubrics.md`.

Two observations from the gate runs bear on the fix pass. The reports'
findings sit in four files (Claude: 28 findings in `memoizer.ts`,
`util.ts`, `schemas.ts` and `mini/schemas.ts`; Codex: 35 in six), and
several merged findings span two of them, so one cluster per file with
merges gives two to four fixers, not twenty. And zod's `lint` script is
`biome lint --write .`: a check the repository defines can itself write
to the tree.

## Goals

- A user of either runtime asks for the review's fixes and receives,
  with no hand on the run, a tree in which every finding that routes to
  a fixer is applied, deferred with a reason or blocked with a reason
  (or, since the amendment, not attempted because the budget ran out,
  the best-ranked having gone first), the project's checks have run
  before and after, and a report says which is which and what changed.
- No two fixers edit one file at the same time, by construction.
- The engine never writes into the reviewed tree. Every byte that
  changes is a fix worker's, and the engine can say afterwards which
  worker changed which file and what it left there.
- A change to the tree that no worker accounts for still stops the run,
  as it does in the read-only review, and the operator can put the file
  back because the run says what it expected there.
- The checks are the repository's own commands, discovered by rule and
  overridable by flag, run one after another in dependency order by the
  engine with the environment pins the pilots found, and a check that
  fails does so with its output frozen as evidence.
- A check the fixers broke gets one repair; a check that was already
  failing before any edit is reported as such and never blamed on them.
- A run interrupted anywhere in the fix pass resumes with the same
  command, and a fixer that runs again on a half-applied cluster is told
  so and reports what it found already done.
- The element is accepted by a real fix run on each runtime on the same
  change the read-only gate used, so the two can be read side by side.

## Non-Goals

- No test assessment and no documentation reconciliation. The proof of
  concept's Step 2 (a reader that checks the fixers' tests are real and
  sends a gap back) and its `DOCS-STEP1` cluster (a fixer that owns the
  documents and takes the fixers' `DRIFT` lines) are each a role, a loop
  and a repair path of their own. They are the next element, 6b, so that
  the first editing run measures editing (PD1). The fixers still add
  tests and still report `DRIFT`, `TESTS` and `VALIDATION` as their
  prompt says; the report carries the lines and nothing acts on them
  yet.
- No audit, no steering, no questions to the author, no replan. What a
  fixer defers or blocks, and every `PLAUSIBLE` design finding, reaches
  the report under "Held for the author" with the fixer's reason. The
  seventh element re-opens them. A finding blocked because its fix
  needs a file another cluster owns gets one second round once those
  clusters have settled (R21, PD18, amended 2026-10-02); a deferred
  finding, a finding blocked for any other reason and a finding blocked
  again in the second round are not re-dispatched, and the audit that
  re-opens them belongs to the seventh element.
- No gate on which routed findings are fixed beyond the run budget.
  A severity floor that holds findings below a chosen severity is
  deferred by the author to a later element (PD20).
- No second repair round. One repair worker after the post-fix checks,
  then the checks once more; a check still failing is reported, with
  the tree as the workers left it (PD9).
- No parsing of check output. A check passes or fails by its exit code;
  what the failure means is the repair worker's reading, with the log
  as evidence (PD8).
- No sandboxing of a fixer to its owned files. Neither runtime offers a
  per-file write allowlist that the neutral contract could carry;
  ownership is a rule in the prompt, and the engine observes what each
  worker changed and records a breach rather than preventing it (PD4).
- No reverting by the engine. A fixer that fails, a violation, a repair
  that does not converge: the tree stays as the workers left it, and
  `git` shows the operator every edit. The engine's only writes are
  outside the tree (PD3).
- No suspend detection for a check, as the runtime adapter left it for
  workers. A machine that sleeps during a check times it out; the
  check's receipt records wall-clock start and end.
- No per-package check graph. Checks are the repository's top-level
  commands, run at its root; a monorepo whose packages need their own
  order names one command that does it (PD7).
- No mixed roles in one phase. Fixers never run while a reader runs,
  and the checks run alone.
- No change to the read-only review's phases, events or report when
  `--fix` is absent, beyond the event versions the wider phase list
  requires (design).
- No convention files for checks. `CLAUDE.md` and `AGENTS.md` often name
  the commands, but a model would have to read them; discovery is by
  manifest and flag (PD6).

## Requirements

- **R1: `--fix` on `review` runs the fix pass after merge and rank, and
  the run pins it.** A run configured with `--fix` records it on its
  configuration; a resumed run keeps it and the flag's absence or
  presence on a later invocation is logged as ignored. A run without it
  runs the read-only phases and the report exactly as element five
  does. A fix run adds, after merge-rank and before the report, the
  phases: baseline checks, fixes, checks, repair (when a check the
  baseline passed now fails), and the repair's checks. Each is started,
  checked against the tree and finished like every other phase, with no
  worker when it has no unit.
- **R2: Findings are routed by verdict and angle, as the rubric says.**
  Every finding of the ranked list that is `CONFIRMED`, or `PLAUSIBLE`
  from a correctness, cost or `CONVENTIONS` angle (its primary's angle,
  `unverified` included), routes to a fixer. A `PLAUSIBLE` finding whose
  primary is from a design angle (`DESIGN`, `DUPLICATION`, `ALTITUDE`)
  is held for the author and no fixer sees it. The routing is recorded
  with the plan and the report shows each finding's route.
- **R3: Clusters are one per file, merged findings are kept whole, and
  no file is in two clusters.** The fixer-routed findings are grouped by
  the canonical path of each finding's primary location, and every
  location of a merged finding's members joins the cluster; when that
  pulls one file into two clusters the clusters are merged, so no file
  is owned twice. An unlocated finding is clustered by its raw path
  spelling, folded as grouping folds it. Clusters are ordered by the rank
  of their best finding and their findings within by rank, so the
  ranking governs the order fixes land. The plan is one event, recorded
  once, so a later engine with another clustering rule resumes the plan
  this run made.
- **R4: A cluster's fixer owns the cluster's files exclusively, may
  edit files no cluster owns, and reports every file it changed.** The
  fixer's task names the files it owns, the files every other cluster of
  the pass owns (which it must not touch; a fix that needs one is
  reported blocked naming the file), and says that any other file of the
  repository, existing or new, may be edited when the fix or its tests
  need it and must be reported. The answer lists, per finding, the
  files edited or created for it; an owned file whose bytes changed and
  that no finding lists fails the answer as a structural check would,
  and the retry is told what the tree already holds.
- **R5: Each fixer's answer is a schema the engine validates, and the
  prose return format is gone.** Per assigned finding, by index: one of
  `applied`, `already-applied`, `deferred` or `blocked`, a location, a
  one-sentence note, the files edited or created for it, a commit
  message for an applied finding (a subject line and a body, in the
  repository's own commit style), zero or more corrections to the brief,
  zero or more validation lines (method and evidence), and, when blocked
  for ownership, the files it needed; per answer: the documentation
  drift lines, the tests added or tightened and the fixer's own suite
  run (result, command, failure lines). Every index appears exactly
  once. The `fixer-report.md` fragment describes the same fields and
  nothing else, in its own commit.
- **R6: The engine observes every fixer's edits, finding by finding,
  and records each as a revision of the tree.** After finishing each
  finding the fixer runs one command the engine ships, which copies
  every changed file of the tree into the fixer's scratch directory
  under that finding's index (R15 says so in the prompt). When the
  answer is recorded the engine reads the snapshots in the order the
  findings were given, and the tree as it is for the last, and freezes,
  per finding, the bytes of every owned file and every file the answer
  names that differ from the state before it (the scope's after state,
  as revised since) into the evidence store, recording one revision per
  finding: the finding's ids, the fixer's message, and for each changed
  path the frozen reference or `null` for a deleted file. A finding
  with no snapshot, or whose snapshot changed nothing, folds into the
  next finding's revision, which then names both ids; the tree's final
  state is the last snapshot whether the fixer took it or not. A
  reported edit to a file another cluster owns is recorded on the
  answer as an ownership violation, frozen like any other, named in the
  report and does not stop the run. Files git reports as new that no
  answer names are recorded as strays at the end of the fix phase,
  listed in the report, and never part of what the run expects.
- **R7: The worktree check holds during and after editing.** What the
  run expects of the tree is the scope's after states overlaid by every
  recorded revision. In a read-only phase, a checks phase and the
  report, the check runs when element five runs it, over every expected
  file. In an editing phase it runs when the phase starts and again
  when its last worker has settled and every answer has been revised
  in, over every expected file that no unanswered unit of the phase
  owns; and everywhere it compares `HEAD` with the scope's head. A
  difference blocks the run with `drift`, naming each file and the
  evidence reference of the bytes the run expected, so the operator can
  restore it, and naming the head when it moved. A run interrupted with
  fixers in flight resumes as element five resumes: their units run
  again, and the fresh fixer's brief says the tree may already hold part
  of the work.
- **R8: Checks are the repository's commands, discovered by rule,
  overridable by flag, and pinned on the run.** Four kinds: `build`,
  `typecheck`, `lint`, `test`. For each kind the engine takes, in order:
  a `--check <kind>=<command>` flag; a Taskfile task, a Makefile target
  or a justfile recipe of that name; a `package.json` script of that name
  (or the aliases the design lists), run through the package manager the
  lock file names; the language default for `go.mod`, `Cargo.toml`,
  `pyproject.toml` and a `.sln` or `.csproj` at the root. `--no-check
  <kind>` drops a kind. A kind with no
  command is recorded as not available. The resolved checks, each with
  its origin, are one event before the baseline runs, and a resumed run
  uses the pinned checks.
- **R9: The engine runs checks one after another, in dependency order,
  contained, with evidence.** `build` first; then `typecheck`, `lint`
  and `test`, in that order, each only when `build` passed or does not
  exist, whatever the other two did. A check is a child process of the
  engine in the worktree with the pinned environment (no build-server
  reuse, non-interactive, no colour, stdin closed) and a timeout from the
  policy; its stdout and stderr are frozen, its exit code, signal and
  wall-clock start and end are recorded, and at the timeout its process
  tree is killed as a worker's is. A check that writes to expected files
  ends its phase with a revision attributed to the checks, so a
  formatter or a generator is not drift.
- **R10: The baseline is run before any edit and decides what a
  failure means.** The baseline phase runs every available check once
  with no fixer dispatched. A check that fails at baseline is reported as
  failing before the fix pass and is still run afterwards, but its later
  failure never triggers a repair. A check that passed at baseline and
  fails after the fixers is what the repair phase takes.
- **R11: One repair, then the checks once more.** When a check the
  baseline passed fails after the fix phase, one repair worker runs in
  the `fixer` role, owning every file the fix phase's revisions name,
  given every failing check's command, exit code and the tail of its
  output plus the frozen log's path, and every fixer's answer; it
  returns the same schema with the failing checks as its findings. The
  checks then run again. A check still failing is recorded and reported;
  the run goes on to the report.
- **R12: Fixers and the repair worker run with edit access under the
  role policy, and the retry rule holds.** `roles/policy.json` gains
  `fixer` and a `checks` block (the per-check timeout); the fixer's
  starting values are the proof of concept's (strong tier, high effort,
  8 USD) with a longer timeout, since a fixer runs the suite more than
  once (design). A fixer that does not complete, or whose answer fails
  its schema or a structural check, is run once more as a fresh worker
  on the same cluster; a second failure records the cluster's findings
  as not attempted and the phase as degraded; a lost worker among the
  failures blocks the phase, as element five's rule says. The fixers'
  and the checks' cost and time enter the run's budget check and its
  statistics. Since the amendment the unit is a batch (R18), each
  failed attempt's edits are recorded when it fails (R20), and the
  budget in an editing phase stops launches rather than blocking (R19).
- **R13: The report says what the fix pass did.** New sections when the
  run fixed: Fixes (every ranked finding in rank order with its route
  and outcome: applied, already applied, deferred, blocked, not
  attempted, held for the author, each with the fixer's note and its
  corrections), Checks (one row per check and per phase: command,
  outcome, seconds, and for a failure the log's path), Changed files
  (every path a revision names, with whether it was created, modified
  or deleted, and which cluster or the checks changed it), and in
  Limitations the ownership violations, the strays, the drift lines and
  the validation lines the fixers returned, the tests they report, and
  the checks not available and why. Statistics gains a row per new
  phase. `status` shows the fix phases' clusters and checks. Beside the
  report the engine writes a patch series, one patch per revision in
  ledger order, each rendered from the frozen bytes of the paths it
  changed (the state before the revision against its state after) with
  the revision's message, so the series applies in order on a tree at
  the scope's state, reconstructs the final tree exactly, and holds none
  of the user's own uncommitted change even in `--worktree` mode; the
  report's header and `status` name the series' directory.
- **R14: The skills say how to ask for fixes and how the fixes get
  committed.** Both skill texts pass `--fix` when the user asks for the
  findings to be fixed or applied, say beforehand that the engine edits
  the working tree through its workers and commits nothing during the
  run, and show the report path as before. After a fix run the skill
  tells the user the edits are in the tree uncommitted, one patch per
  finding, and offers to commit them; when the user says so it runs
  `deep-review commit` (R17), asking the user for the message of their
  own change first in `--worktree` mode, and shows the commits the
  command printed. Neither skill reviews, fixes, reverts or commits
  anything itself, and neither amends or pushes. The plugin and skill
  descriptions no longer say "editing nothing".
- **R15: The prompts change in their own commits.** `fixer-role.md`
  states the ownership rule of R4; `fixer-report.md` the schema of R5
  and the message each applied finding carries; `fixer-apply.md` says
  to run the snapshot command the task names after each finding, before
  starting the next; `fixer-tests.md` says logs go under the scratch
  directory; the
  narration of the fix pass a fixer needs (that the engine clusters,
  dispatches and runs the checks, and what its answer feeds) replaces
  the proof of concept's Step 1 text where the fixer reads it. The
  `documentation`, `answer` and `test-assessment` roles, which share
  fragments with `fixer`, change with them and are still not run.
- **R17: `deep-review commit` turns a completed fix run's revisions
  into commits, one per revision, after the run and on request.** The
  command takes the run (the last completed fix run by default), refuses
  when the run has no report or no revision, when `HEAD` is not the
  scope's head, when any revised path's bytes differ from its last
  revision, or when the run's commits were already created, and names
  the reason. In `--worktree` mode it first commits the captured change
  itself, from the scope's frozen after states, with the message
  `--change-message` gives, and refuses without one; in the other modes
  the flag is refused. Then, in ledger order, one commit per revision:
  a finding's revision with the fixer's message and a trailer naming
  the run and the finding ids, angle and verdict; a repair revision
  with the repair worker's message for the check it made pass; a
  check's own writes with a message the engine composes. The commits
  are built from the frozen bytes with git's plumbing, with the author
  and committer git takes from the user's configuration, and no file in
  the worktree is written; the branch (or a detached `HEAD`) is moved
  to the last commit only when every commit was built, with a
  compare-and-swap against the head the command started from, and the
  index is reset to the new head so the tree shows clean. The command
  runs no commit hook and says so. Each commit's hash is recorded on
  the run's ledger, and the command prints them, one per line, with
  the subject of each.
- **R16: The element is accepted by a real fix run on each runtime.**
  The gate is the read-only gate's change, zod #6530, run with `--fix`
  once with Claude Code and once with Codex from a fresh clone each, to
  a report with no hand on the run. The design's Verification records
  each run's statistics, the checks' outcomes at baseline, after fixes
  and after repair, the fixers' outcomes per finding, the ownership
  violations and strays, and the author's reading of the two diffs
  against the findings. Amended 2026-10-02: the gate runs on the engine
  as amended, Claude Code first and then Codex, each from a fresh
  clone; the first Claude run, on the engine before the amendment, is
  recorded in Verification as the evidence the amendment answers and
  does not count as the gate.
- **R18: A cluster's findings are fixed in batches, one after another,
  best-ranked first across the run.** (Added 2026-10-02.) The plan
  splits each cluster's findings, in rank order, into batches of at
  most the policy's batch size, four by default, which `roles/policy.json`
  sets and a fix run pins with its configuration. Each batch is one
  fixer unit owning its cluster's files,
  and a cluster's next batch launches only when its previous batch has
  settled, answered or not attempted, so a file still has one editor at
  a time. Batches of different clusters take the run's concurrency in
  the rank of their best finding, so the best-ranked findings of the
  whole run are fixed first. The batches are recorded with the plan.
  The fixer's task names the findings of its cluster's earlier batches
  with their outcomes, since their edits are already in the tree. The
  report and `status` name each finding's batch.
- **R19: In an editing phase the run budget stops new launches instead
  of blocking the run.** (Added 2026-10-02.) When the spend the budget
  check counts reaches the run budget during the fixes or the repair
  phase, every unit of the phase that has not been launched, or has
  failed once and not been launched again, is recorded not attempted
  with the budget as the cause; units already running finish; the phase
  finishes degraded and the run goes on through the checks to the
  report, which names those findings "not attempted (budget)". The
  read-only phases still block at the budget, as element five does. A
  runtime that reports no cost has no cutoff, as it has no budget.
- **R20: A failed attempt's edits are recorded when it fails, from its
  snapshots.** (Added 2026-10-02.) When an attempt of an editing unit
  ends without a recorded answer (a timeout, a failed exit, an answer
  its schema or a structural check refuses) or its worker is found lost
  on resume, the engine records, with that failure, one revision per
  finding the attempt snapshotted, attributed to that finding, and one
  last revision naming no finding for what the attempt left after its
  last snapshot, over the unit's owned files and the paths its
  snapshots listed that no other unit of the round owns. The retry
  starts from an expected tree that holds that work, so its own
  snapshots attribute only its own edits. A retry that verifies such a
  finding as already applied gives the finding's commit message, and
  the patch and the commit of that finding's revision carry it; without
  one they carry a message the engine composes.
- **R21: Findings blocked only on files other clusters owned get one
  second round.** (Added 2026-10-02.) When every unit of the first
  round has settled, each finding a fixer reported blocked whose
  required files are all owned by other first-round clusters is planned
  again: its files are its cluster's files and its required files, the
  findings are clustered and batched as in the first round, the plan is
  recorded once, and the round runs in the same fixes phase on the tree
  the first round left, its fixers owning their new files. A finding
  blocked again, or blocked for another reason, stays blocked; there is
  no third round. The report shows a finding's last outcome and, for a
  finding of the second round, the files it was first blocked on.
- **R22: A file changed when git would store it differently.** (Added
  2026-10-02.) Wherever the run compares a file with a state it
  expected (the worktree check, the revisions, the structural check of
  an answer, and the commit command's refusal), two states are the same
  when their bytes are equal or when git's clean conversion for that
  path (line endings under `core.autocrlf` or the repository's
  attributes) gives the same blob. A patch is the difference between
  those converted contents, as `git diff` shows it. The snapshot command
  copies what `git diff` against `HEAD` reports changed, the untracked
  files and the paths the engine lists, rather than what `git status`
  reports. The evidence stays the raw bytes the tree held, so the drift
  blocker still names bytes that, restored, satisfy the check.
- **R23: The snapshot command starts no process.** (Added 2026-10-03.)
  When it launches an editing worker the engine writes, beside the
  snapshot directory, a manifest of the worktree: every file git does
  not ignore, with its size and modification time, and the directories
  git ignores. The snapshot command lists a path when its size or time
  differs from the manifest, when it is not in the manifest and lies
  under no ignored directory, or when it is gone, plus the paths the
  engine expects as before, and copies them; it reads no ledger and
  starts no git. The engine leaves out a listed path git ignores when
  it reads the snapshots, so a stray log a fixer writes is not taken as
  its work. On Codex's Windows sandbox, where a worker's process cannot
  start another, a fixer's snapshots then work as on every other
  runtime.

  Corrected 2026-10-04: the cause given here is not what happens. A
  later probe with `codex sandbox` (codex-cli 0.160.0) found that under
  the unelevated sandbox a process cannot create a named pipe, through
  which Node gives a child its piped stdio, so a spawn whose stdio is
  `pipe` fails with `EPERM` while the same spawn with stdio `inherit`
  or a file runs. Processes do start; the pipe is refused. `spawnSync
  git` captures its output and does fail, so R23 stands unchanged
  (`docs/changes/2026-10-04-codex-sandbox.md`).
- **R24: A check that fails before and after the fixes is read for
  new failures.** (Added 2026-10-03.) A kind that failed at baseline and
  fails or times out after the fixes goes to the repair worker beside
  the kinds the fixes broke, with its output from both runs; its task
  says to fix the failures the baseline output does not show and to
  answer `deferred` when there is none. Every fixer's task names the
  kinds that failed at baseline with the frozen outputs' paths, and says
  a failure those outputs do not show is its own. Which failures are new
  is the repair worker's reading; the engine still parses no output.
- **R25: The fixer's timeout is 1800 s.** (Added 2026-10-03.) In the
  policy, for both runtimes; the checks keep 1200 s.
- **R26: Claude's default run budget is 60 USD.** (Added 2026-10-03.)
  In the policy's runtime entry; `--budget-usd` still sets a run's.
- **R27: The log names a revision that serves no finding as one.**
  (Added 2026-10-03.) A failed attempt's closing revision is logged as
  "revised N files after its last snapshot", not as revised "for"
  nothing.

## Product Decisions

- **PD1: The element is editing and checks; test assessment and
  documentation reconciliation are the next one.** Carrying the whole
  proof-of-concept fix loop, as element five carried the whole read-only
  pipeline, was considered and rejected: element five's argument was
  that a report without merging is a list, whereas a fix pass without an
  assessor is still a fix pass, with its tests in the diff for the
  author to read. Each of the two loops left out is a reader role, a
  verdict schema, a repair route and a gate of its own, and the first
  editing run should measure editing. The fixer's prompt keeps asking
  for the tests and the drift lines, so the next element adds readers,
  not writers.
- **PD2: The fix pass is opt-in by flag, in the same run.** Editing by
  default was rejected for this element: the skill texts promise a
  report that edits nothing, and a user who has not read the findings
  should not find the tree changed; the default is reconsidered when
  the seventh element completes the loop the skill describes. A separate
  `fix` command that continues a completed read-only run was rejected:
  a finished run is closed (element five, R1), the fix phases need the
  worktree the review saw, and a user who wants to read first runs
  without the flag and then with it, paying the review twice, which is
  the price of reading first until a continuation is designed with the
  audit.
- **PD3: The engine never writes into the reviewed tree during a
  run.** Reverting a failed fixer's edits from the frozen bytes,
  restoring a violated file to what its owner left, or cleaning strays,
  were each considered and rejected together: an engine that writes the
  tree is a second editor whose edits no worker reported, the operator
  can no longer read the tree as "what the workers did", and every
  revert needs a rule for the user's own uncommitted work in the same
  file. `git` shows every edit, and the report names every file. The
  cost is that a broken tree is left broken, named. The one write the
  engine makes is after the run, on request, and to the repository's
  objects, refs and index, never to a file of the tree (PD13).
- **PD4: Ownership is a rule the prompt states and the engine
  observes, not a sandbox.** Enforcing it through the runtimes was
  rejected: Claude Code's permission rules could name paths but the
  neutral contract does not carry them, and Codex's sandbox is a
  directory, not a file list. The proof of concept observed ownership
  after each wave and blocked the run on a violation with no retry;
  here a violation is recorded on the answer, frozen and reported, and
  the run continues, because the answer that reports its edits is
  telling the truth and the checks that follow judge the result. The
  case the rule protects against, two fixers in one file at once, is
  ruled out by clustering (R3), so a violation is a fixer that reached
  into a settled or in-flight sibling's file and said so.
- **PD5: A fixer may edit any file no cluster owns.** The proof of
  concept's rule, owned files only, with a planner that could add
  existing test files from the captured change, was rejected: it is the
  rule behind the main defect the engine problems record (a test that
  belongs in an untouched file could not be owned) and it took three
  mechanisms to administer. Free editing of unowned files gives up one
  guarantee, that two fixers never touch one shared test file, and keeps
  the one that matters, that the finding files are owned once. The risk
  is accepted below; the fixer reports every file, so the report shows
  when two clusters touched one.
- **PD6: Checks are discovered by manifest and flag, not by a
  worker.** A discovery worker reading the rules files was rejected for
  now: it puts a model's reading in the control flow before the first
  measurement of the mechanical rule, and the gate repository is found
  by the rule. The proof of concept's precedence (flag, Taskfile,
  Makefile, justfile, `package.json`, language default) is kept, with a
  `build` kind added because the pilots filed compile steps under
  `typecheck` for want of it. A flag names the command a rule cannot
  find.
- **PD7: Checks run strictly one after another, `build` first, and the
  other three run whatever each other did.** Running checks at once was
  rejected on the pilot's evidence of shared build output. Stopping the
  chain at the first failure, as the proof of concept did, was rejected
  for the three that do not depend on each other: a lint failure says
  nothing about the tests, and one round should give the repair worker
  every failure at once. `build` is the exception because the others
  read what it produces.
- **PD8: The engine does not parse check output.** The proof of
  concept's per-tool parsers and its `unsupported-check` blocker were
  rejected: they were the most code on the editing path, a stray stderr
  line disabled them, and the question they answered (is this failure
  the reviewed code's or the environment's) is one the baseline run
  answers for the environment and the repair worker answers for the
  code, reading the log. A failing check gives the repair worker its
  exit code and its output; that is what a person would read.
- **PD9: One repair round.** Unbounded rounds were rejected as the proof
  of concept's own decision records (PD3 there: unlimited repair can
  consume resources without converging); zero were rejected because a
  fixer that breaks a check it did not run is the common case a second
  look fixes. One round is the smallest number that gives the fixers'
  work a chance to pass; the gate measures whether it is enough.
- **PD10: The baseline run is part of the pass.** Skipping it, and
  treating every post-fix failure as the fixers' fault, was rejected: a
  repository whose tests fail on the machine, or whose lint is red on
  `main`, would send a repair worker after failures no edit caused, and
  a missing tool would surface only after the fixers had spent their
  budget. The baseline costs one run of the checks and no model.
- **PD11: Drift during editing is "an expected file changed that no
  answer accounts for", checked when an editing phase starts and when
  it ends, and the expected tree follows the revisions.** Suspending
  the check during the fix phase was rejected: the read-only review's
  guarantee, that an unaccounted change blocks, would lapse exactly when
  the tree is being edited. Keeping element five's check before each
  answer was rejected: a fixer legitimately edits unowned files (its
  tests) while its siblings run, and the proof of concept's binding of
  each editor to one tree is what classified a deferring editor as drift
  because its siblings had edited. Comparing the whole tree, as the
  proof of concept did, was rejected as the source of its drift dead
  ends. The expected tree, scope plus revisions, is what the run can
  vouch for; a stray file is listed, not blocked, because a scratch file
  cost a whole pilot run (D3) and a stray cannot corrupt a fix.
- **PD13: The commits are built after the run from the frozen bytes,
  on request, not by the fixers as they go.** The fixers committing in
  their sessions, after each finding, was weighed in full. It would buy
  granularity for free, messages written with the diff in view, and the
  repository's hooks running as they do for a person. It was rejected on
  two walls and three costs: Codex's sandbox keeps `.git` read-only, so
  one runtime could not commit at all; the branch would move under a
  run nobody has read, and an abandoned run would leave partial fix
  commits on it; parallel fixers would share one index and one branch,
  so a `git add` by one could ride into another's commit and a fixer
  killed mid-commit would leave `.git/index.lock` to stop every later
  git call; `HEAD` moving during the run would have to be followed by
  the drift check and the range rule; and a hook that fails or
  rewrites files would be a fixer failure the engine sees only as an
  exit code, with Claude Code's own commit trailer added unless the
  prompt manages to forbid it. Building the commits later from the
  revisions is one behaviour on both runtimes, touches no file, moves
  the branch only when asked and only to a state the tree already
  holds, and can be rebuilt from the ledger after a crash. What it gives
  up is recovered where it can be: the fixer still writes each message
  with the diff in view, as a field of its answer (R5); the granularity
  comes from the snapshot the fixer takes after each finding (PD14);
  the hooks it does not run are named in Risks. Leaving the user with
  one commit, or with `git diff` alone, was the earlier draft, rejected
  because one commit of several fixes is not how this repository or the
  gate repository is written, and in `--worktree` mode the change under
  review and the fixes share the files, which is why the command commits
  the captured change first from its own frozen bytes. Having the
  skill's model run the git steps itself was rejected once the steps
  held a reverse-apply, a sequence of commits and an index reset: that
  is a procedure, and a procedure belongs in the engine where it runs
  the same on both runtimes and is tested.
- **PD14: Per-finding granularity comes from a snapshot the fixer
  takes after each finding, not from one fixer per finding.** One
  fixer per finding is logical by construction and was rejected on
  cost: on the gate change it is about twenty-eight fixers instead of
  three or four, each re-reading the same file, and serial within a
  file. The snapshot is one command run after each finding, which
  copies the changed files into the fixer's own scratch; a missed
  snapshot folds that finding into the next one's commit and the
  message names both, so the worst case is the granularity a fixer
  that forgot to commit would have given, never a wrong tree, since the
  final state is the tree itself. Asking the fixer to copy files by
  hand was rejected in favour of the command because a copy a model
  does by hand misses files; the command copies what git reports
  changed.
- **PD12: The gate repeats the read-only gate's change.** A new change
  was rejected: the value of the first editing run is in reading its
  diff against findings the author has already read on both runtimes.
  Whether the Tarkov pilot repository, whose .NET build servers and CRLF
  checkout are the origin of half the problems above, runs as a third
  gate on one runtime is the design's open question, recommended yes.
- **PD15: Batches, four findings by default, one after another within
  a cluster, rather than a longer timeout.** (Added 2026-10-02.) On the first gate run
  one cluster held 18 of the 20 fixer findings, as the Risks below
  foresaw, and its fixer was killed at its 1200 s timeout two minutes
  after snapshotting its last finding, while it ran the suite. A
  timeout scaled to the finding count was rejected: it bets the whole
  cluster on one session, and a retry starts that session over. One
  fixer per finding stays rejected on PD14's cost. Running two batches
  of one cluster at once was rejected because it puts two editors in one
  file, which clustering exists to rule out. The size is a policy
  value, as the fixer's timeout is, because the two are tuned together;
  a constant in the code was rejected by the author. Four is the
  default because it is the size of the first gate run's best-ranked
  group, its four major findings at the top of one cluster; the second
  gate run's times say whether it holds, and the default moves with
  them.
- **PD16: The budget ends the fix pass's launches, not the run.** (Added
  2026-10-02.) Blocking at the budget in an editing phase, as the
  read-only phases do, leaves edits in the tree with no report saying
  what they are, the worst outcome the run can have. Reserving each
  batch's per-worker cap before launching it was rejected as too
  cautious: on the first gate run the review left 14 USD of 30, which
  would have launched one batch at a time. The read-only phases keep
  blocking: a review cut short has no ranked list to fix from, and its
  report would mislead.
- **PD17: A failed attempt is read from its snapshots.** (Added
  2026-10-02.) Recording a unit's leftover edits only when it fails for
  good, as the first implementation did, cost the first gate run the
  per-finding record of 14 findings: the retry found the first
  attempt's edits in the tree, verified them as already applied, and
  its first snapshot took all of them under one finding, a blocked one.
  The first attempt had snapshotted every one of its 18 findings, each
  snapshot changing exactly the files of its finding. Recording the
  difference of the tree as one revision at the failure was rejected
  because it throws that record away.
- **PD18: One second round for ownership blocks, reversing a
  Non-Goal.** (Added 2026-10-02.) The first proposal left every blocked
  finding to the seventh element's audit. On the first gate run that
  left the three best-ranked findings unfixed: their fix flips
  assertions in a test file that a one-finding cluster owned, and that
  cluster had finished in 148 s. Moving a file's ownership while a
  round runs was rejected: it needs a scheduler with dependencies
  between units, harder to reason about and to test, to gain only wall
  time. Adding test files to clusters when planning was rejected because
  which test a fix needs is known only once a fixer has read the code.
  Letting a fixer edit another cluster's file stays rejected (PD4, two
  editors). A third round was rejected: a finding blocked twice needs a
  person, which is the audit's job.
- **PD19: A change is what git would store, and git does the
  conversion.** (Added 2026-10-02.) On the first gate run zod's
  `postbuild` (`biome format --write .`) rewrote a CRLF checkout to LF;
  the build check's revision was a 965 KB patch of line endings, and
  `git status` listed 449 changed files where `git diff` listed the 10
  the fixers edited. Converting line endings in the engine was rejected
  as a second copy of git's rules (`core.autocrlf`, `core.eol`, the
  `text` and `eol` attributes) that would drift from git's. Asking users
  to turn `core.autocrlf` off was rejected: Git for Windows installs it
  on. Ignoring carriage returns in comparisons was rejected as wrong for
  a repository whose index holds CRLF.
- **PD20: No gate on which routed findings are fixed beyond the
  budget.** (Added 2026-10-02.) With batches in rank order and the
  budget cutoff, what is fixed first and where fixing stops follow the
  ranking and the money, both already recorded. A cap on the number of
  findings was rejected as an arbitrary second budget. A model pass
  that judges which findings are worth fixing was rejected as another
  judgment and another cost, and as the seventh element's audit built
  early. Fixing only findings on changed lines was rejected because it
  drops the `RIPPLE` angle's findings, which sit in unchanged callers by
  definition. Holding `CONFIRMED` design findings for the author would
  reopen R2 and is a product question of its own. An opt-in severity
  floor was considered and deferred by the author to a later element.
- **PD21: The snapshot reads a manifest rather than git.** (Added
  2026-10-03.) Inside Codex's Windows sandbox no process a worker starts
  may start another: git, `cmd.exe` and node itself all fail with
  `EPERM` from node, while the worker's shell can start them (a probe
  through `codex exec` with the adapter's settings, recorded in the
  design). Having the fixer's shell run git and pipe its output to the
  command was rejected: the command line would depend on the shell the
  runtime gives, and PowerShell 5.1 does not pipe NUL-separated bytes
  intact. Parsing `.git/index` in the command was rejected as a second
  copy of git's index format, split and sparse indexes included. A
  manifest of sizes and times taken by the engine, which runs outside
  the sandbox, needs no git in the command and compares against the
  tree at launch, which is what a fixer's work is a change from.

  Corrected 2026-10-04: git, `cmd.exe` and node failed because the
  probe's node script captured their output, not because a worker's
  process may start no other. Under the unelevated sandbox a process
  cannot create a named pipe, and Node gives a piped child its stdio
  through one; started with stdio `inherit`, `ignore` or a file, the
  same processes run (`docs/changes/2026-10-04-codex-sandbox.md`). The
  decision is unchanged: the snapshot command would capture git's
  output, and a manifest read starting no process works under every
  sandbox.
- **PD22: A check failing at baseline still gets one reader after the
  fixes.** (Added 2026-10-03.) On the gate, `test` failed at baseline
  from the environment, the bundle-size suite did not even run there,
  and three of its tests failed after the fixes; the fixers saw them and
  judged them pre-existing against the batch before, not against the
  head. Comparing failures by test name was rejected again (PD8): it
  needs a parser per tool. Leaving it to the fixers alone was rejected:
  each saw only its own batch. The repair worker already reads logs as a
  person would; giving it both outputs of a kind that failed throughout
  costs one strong worker on a run whose baseline is red, and costs
  nothing on one whose baseline is green.
- **PD23: The timeout and the budget move with the gate's
  measurements.** (Added 2026-10-03.) On Codex one fixer batch timed out
  at 1200 s and two took 1081 and 1125 s, one of them holding a single
  finding, so a smaller batch would not have helped; 1800 s gives the
  slowest observed batch a margin of half its time. A per-runtime timeout
  was rejected until a runtime needs a different one. Claude's fix run
  spent 29.07 USD of 30, so 30 is the cost of a run, not a ceiling over
  it; 60 leaves a fix run room and still bounds a runaway, and the
  read-only review, which spent 13 to 16 USD, is unaffected.

## Risks

- Risk: two fixers edit one file that no cluster owns (a shared test
  file, a fixture) at the same time, and one edit is lost. Accepted
  (PD5); each runtime's edit tool re-reads the file before writing, the
  window is small, both fixers report the file, the checks judge the
  result and the report names the file twice.
- Risk: a check the repository defines writes to the tree (`biome lint
  --write` in zod), so a "check" reformats the fixers' edits or the
  user's own uncommitted work. Accepted; the revision after the checks
  records what changed and the report names it, and `--check` names a
  read-only command when the user wants one.
- Risk: a fixer's edits stay in the tree when its answer fails, is set
  aside after a drift, or the worker is lost, and the retry works on a
  half-applied cluster. Accepted (PD3); the prompt already treats an
  applied finding as a success to verify, and the brief says the tree
  may hold earlier work. Since the amendment those edits are recorded
  when the attempt fails (R20), and the retry's task names the findings
  they belong to.
- Risk: an orphaned fixer from a hard kill of the engine may still be
  editing when the resumed engine dispatches its replacement, and two
  editors work one cluster. Accepted, as element five accepted the
  double payment for a reader; the launcher's tree kill covers every
  ordinary exit, and the resumed run's drift check catches the orphan's
  later edits as unaccounted.
- Risk: a check runs arbitrary code the repository defines, in the
  engine's process tree, with the user's credentials. Accepted; the
  read-only review already gives every worker a shell in the same tree,
  and the commands are the repository's own.
- Risk: a check that hangs costs its full timeout, and a suspended
  machine times it out. Accepted, as the runtime adapter accepted it for
  workers; the receipt records wall-clock start and end.
- Risk: a merged finding can pull most of the findings into one cluster
  (on the gate change, the four files hold every finding and two merges
  span them), so one fixer does most of the work serially and
  concurrency buys little. Accepted; a finding kept whole is worth more
  than parallelism, and the timeout is per worker. The first gate run
  showed the cost (one cluster of 18 findings, its fixer timed out), and
  batches answer it (R18); the cluster is still worked serially.
- Risk: the fix run costs more than the read-only run, and the 30 USD
  default may stop a Claude fix run mid-pass. Since the amendment the
  pass stops launching at the budget and reports what it did not
  attempt (R19); a higher `--budget-usd` on a new run fixes more, the
  gate measures the cost, and the policy default moves with it.
- Risk: batches serialize a large cluster, and the second round waits
  for the slowest unit of the first, so a fix run takes longer than one
  fixer per cluster would when that fixer finishes in time. Accepted
  (PD15, PD18); a batch that times out loses its own findings only.
- Risk: the budget cutoff lets the units already running finish, so
  spend can pass the budget by up to their per-worker caps. Accepted,
  as element five accepted the same overshoot; the report shows the
  spend.
- Risk: a failed attempt's snapshot lists a path outside its owned
  files that a sibling was editing at that moment, and the sibling's
  partial edit is attributed to the failed attempt's finding. Accepted;
  the expected tree is still right, the sibling's later revision holds
  the rest, and only the attribution of a shared unowned file blurs, as
  PD5 already accepts for such files.
- Risk: a second-round fixer changes a test that pins the reviewed
  change's own behavior, because the finding says that behavior is
  wrong (on the first gate run, `cyclic-data.test.ts` asserts a forward
  getter is recursive). Accepted; the finding was confirmed by a
  verifier before it reached a fixer, the fixer's note says what it
  flipped and why, and the test's change is in the finding's own patch
  for the author to read.
- Risk: without test assessment (PD1) a fixer's tautological test
  reaches the diff unremarked. Accepted for this element; the fixer's
  own prompt forbids it, the report carries the `TESTS` lines, and the
  next element adds the reader.
- Risk: ownership violations are recorded, not prevented (PD4), so a
  fixer that ignores its prompt can write over a sibling's settled fix.
  Accepted; the answer that reports it is the evidence, the checks run
  on the result, and a violation on the gate is a reason to revisit.
- Risk: the commit command runs no `pre-commit` hook, since it builds
  commits from blobs rather than through `git commit`, so a repository
  whose hook formats or checks code gets commits a person's commit would
  have formatted or refused. Accepted (PD13); the checks ran on the same
  tree, the command says it ran no hook, and the alternative, porcelain
  commits at every intermediate tree, has the engine rewriting the
  worktree once per finding.
- Risk: a fixer that misses snapshots gives coarser commits than the
  findings, down to one commit for the cluster. Accepted (PD14); the
  report names which findings each commit holds, and the gate's runs
  show how often it happens.
- Risk: in `--worktree` mode the command commits the user's own change
  first with a message the user supplies at that moment, which is later
  than a person would usually write it. Accepted; the alternative is
  one commit of both, which was the earlier draft's cost.
- Risk: a user who edits a revised file after the run and before
  committing is refused by the command and must undo the edit or
  commit by hand from the patch series. Accepted; a commit built from
  frozen bytes that does not match the tree would leave the tree dirty
  against its own head.
- Risk: `HEAD` joins the drift check, so a user who commits during a
  fix run blocks it, and must reset to the recorded head or abandon.
  Accepted; a commit under a running review is the case the check is
  for, and the block names the head.
- Risk: on Codex's unelevated Windows sandbox a fixer cannot run the
  repository's checks, since `pnpm` and the tools it starts are
  processes a worker's process may not start; its validation is what
  its shell and node can do directly. Accepted; the engine runs the
  checks itself after the fixes, the repair reads them, and Codex's
  elevated sandbox, a one-time setup on the machine, is the operator's
  way to give fixers their checks.
- Risk: a manifest compares sizes and times, so an edit that keeps a
  file's size within the same tick of its time is not listed by a
  snapshot. Accepted; the path is then read from the next snapshot or
  the worktree, so the work is still recorded, under a later finding.
- Risk: R24's repair worker may "fix" a failure that was environmental
  and only looked new, such as a suite the baseline never reached.
  Accepted; its answer and its revision say what it changed and why,
  and the repair checks run after it.
