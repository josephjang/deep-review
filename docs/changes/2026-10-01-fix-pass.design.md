# Technical Design: Fix pass

Product part: [2026-10-01-fix-pass.requirements.md](2026-10-01-fix-pass.requirements.md).

## Summary

Five phases join the review's fixed order between merge-rank and the
report when a run is configured with `--fix`: baseline checks, fixes,
checks, repair, repair checks. The planner, the controller loop and the
retry rule are element five's; what is new is one kind of unit that
edits (a cluster of findings given to a `fixer` worker with `access:
'edit'`), one kind of step that runs a repository command instead of a
worker (a check), and one more source of truth about the tree beside the
scope: the revisions, each recording the bytes a worker or a check left
in the files it changed. The expected tree, scope overlaid by revisions,
is what the worktree check compares against from then on, so an edit a
worker reported is not drift and an edit nobody reported still is. A
fixer snapshots its files after each finding through a subcommand, so
the revisions are one per finding and the report's patch series and
the post-run `commit` subcommand, which builds one commit per revision
from the frozen bytes with git's plumbing, are both views of the
ledger. Seven new event kinds carry the plan, the checks, each fixer's
answer, each revision, each cluster's degradation and the commits; the
five events that name a phase get a version 2 with the wider phase
list, and the fold exposes the fix pass as `ReviewState.fix`. Check
discovery is a pure function over the repository's manifests and the
command's flags, and check execution is `runProcess` with the platform
shell as the executable and the same environment pins the workers get.

## Non-Goals

- No new role prompt. The `fixer` role runs the fixes and the repair;
  `documentation`, `answer`, `test-assessment` and `auditor` stay
  unrun, and no fragment is written for a role this element does not
  run.
- No continuation of any session. A retried fixer is a fresh worker, as
  every retry in element five is; the Claude continuation budget
  question stays open.
- No change to the runtime adapters, the launcher or the scope capture
  beyond what is named under Design: the launcher's environment pins
  are reused by the check runner, `freezeBytes` and `readWorktree` are
  reused by the revision, and `matchesFrozen` is exported from the
  compare module.
- No change to the read-only phases' events, tasks or schemas. A run
  without `--fix` appends the same kinds it does today, at the new
  versions where a phase name is carried, and folds to the same state
  plus `fix: null`.
- No parsing of any check's output, no test-file classification, no
  per-file check scoping, no path aliasing beyond the canonical spelling
  the locations module already produces.

## Design

### Command line (R1, R8)

```
deep-review review  ... [--fix] [--check <kind>=<command>]... [--no-check <kind>]...
```

- `--fix` is a boolean flag of `review`. It is read only when a run is
  configured: the configuration records `fix: true`, and a resumed run
  logs the flag's presence or absence as ignored, like the model flags.
- `--check <kind>=<command>` names the command of one kind, `build`,
  `typecheck`, `lint` or `test`; a kind named twice is a usage error.
  `--no-check <kind>` removes a kind from discovery. Both are read only
  when a run is configured and both are refused without `--fix`.
- Two subcommands join `review`, `status` and `abandon`: `snapshot
  --finding <n> --into <dir>`, which a fixer runs (Snapshots), and
  `commit [--run <id>] [--change-message <text>]`, which a person runs
  after a fix run (The commit command).
- Everything else is as element five left it. `status` prints the fix
  phases (below).

### Phases (R1)

The phase list, in `src/review/vocabulary.ts`, becomes:

```
triage, finders, deduplication, verification, sweep, sweep-deduplication,
sweep-verification, merge-rank,
baseline-checks, fixes, checks, repair, repair-checks,
report
```

A run whose configuration has `fix: false` has the five fix phases in
its `phases` record with status `skipped`, a new `PhaseStatus` the fold
gives them at configuration; `phaseStarted` treats a skipped phase as
done when it checks that every earlier phase has finished, and the
planner's "next pending phase" passes over them. So the read-only review
appends exactly the events it appends today, and its report renders the
same.

| Phase | Units | Role | Degradation after two failures |
|---|---|---|---|
| baseline-checks | none (the engine runs the checks) | | |
| fixes | one per cluster | `fixer` (`access: 'edit'`) | `cluster.failed@1`; the cluster's findings are "not attempted" |
| checks | none; only when the fixes phase recorded a revision | | |
| repair | one, only when a check that passed at baseline failed in `checks` | `fixer` (`access: 'edit'`) | `cluster.failed@1` with key `repair` |
| repair-checks | none; only when the repair phase had a unit | | |

A phase with no unit and nothing to run is started, checked and finished
`completed` in three appends, as element five does for an empty sweep.
The checks phases have no unit but do have work; the planner gives them
steps of their own (below).

### Routing and clustering (R2, R3)

`src/review/fixes.ts`, pure over the fold:

- `routeOf(finding)`: `fixer` when the resolution's verdict is
  `CONFIRMED`, or `PLAUSIBLE` and `angleClasses[primary.angle]` is
  `correctness`; `held` when `PLAUSIBLE` and the class is `design`.
  `unverified` does not change the route, as the rubric says.
- `planClusters(findings)`: for every fixer-routed finding in rank
  order, its file set is the canonical `file` of its primary and of each
  member that is located; an unlocated candidate contributes its
  `rawFile` normalized as grouping normalizes an unlocated path (slashes,
  `./`, lower case) under a marker that keeps it apart from real paths.
  Clusters are the connected components of findings over shared file
  keys, in the order of their first finding; a cluster's `files` are its
  real paths (the markers own nothing), and its `findings` are in rank
  order. Cluster ids are `c<n>`. The plan is appended once as
  `fixes.planned@1` at the fixes phase's first attempt, before any
  launch, and a resumed run reads it.
- Paths are compared as strings: every located path is already in the
  worktree's own spelling (locations, element five), so two spellings of
  one file meet before they get here, and a case-insensitive file system
  is handled where the spelling was chosen (scope capture, D6).

### The expected tree and revisions (R6, R7)

`src/review/tree.ts`:

- `expectedTree(state): ReadonlyMap<path, FrozenFile | null>` is the
  scope's after states (`null` for a deleted file) overlaid, in ledger
  order, by every `tree.revised@1`'s files. A revised path that the scope
  did not hold enters the map; a revision recording `after: null`
  expects the path absent.
- `compareExpected(expected, worktree, excluded)` gives, for every
  expected path not in `excluded`, `unchanged`, `modified`, `deleted` or
  `restored`, through `matchesFrozen` and `readWorktree`; plus `head`,
  the current `HEAD` against the scope's, as
  `{ expected, actual } | null`.
- `reviseFrom(evidence, read, expected, paths)` reads each path through
  `read` (the worktree, or a snapshot directory standing in for it),
  compares with the expected state and returns the revision entries for
  those that differ: `{ path, status: 'created' | 'modified' |
  'deleted', after: FrozenFile | null }`, freezing through
  `freezeBytes`. A path that does not differ yields nothing.
- `revisionsFromSnapshots(evidence, worktree, snapshots, expected,
  paths, findings)` folds a fixer's answer into revisions: for each
  finding in task order that has a snapshot, the entries of
  `reviseFrom` over that snapshot against the state so far, attributed
  to the finding; a finding without a snapshot, or whose entries are
  empty, is carried to the next revision's ids; the last revision reads
  the worktree, so the tree's final state closes the sequence whatever
  the fixer snapshotted. A snapshot that lacks a path the worktree holds
  is read as that path absent only when the snapshot's listing says so,
  else the path is taken from the next snapshot that has it.

The controller's worktree check becomes `compareExpected` everywhere
`driftedFiles` ran. What is excluded depends on the phase:

- In a read-only phase, the checks phases and the report: nothing.
- In `fixes` and `repair`: the files owned by every unit of the phase
  that has no recorded answer (in flight, not yet launched, or lost),
  since a fixer's edits to its own files are the phase's purpose and a
  lost fixer's half-applied edits are what its replacement is told to
  expect. The per-answer check of element five is not run in these two
  phases; instead the check runs once more when the phase's last unit
  has settled and before `phase.finished` (the planner's `finish-phase`
  is preceded by a `check-worktree` with `moment: 'end'`), over the whole
  expected tree, so a change that no answer accounted for blocks the
  phase as drift.

`worktree.checked@2` carries `phase`, `attempt`, `moment: 'start' |
'answer' | 'end'`, `drifted`, `head: { expected, actual } | null`,
`files: [{ path, outcome, expected: FrozenFile | null }]` (the expected
state, so the blocker and the report can name the bytes to restore) and
`strays: string[]`, the paths git reports as untracked at that moment
that the expected tree does not hold, listed and not counted as drift.
`drifted` holds exactly when `files` is non-empty or `head` is not null.
The `drift` blocker's detail names each file with the evidence path of
its expected blob, or "expected absent", and the head when it moved,
cut to the frozen cap with a count of the rest; its action gains the
sentence "the files named hold the bytes the run expected at the
evidence paths given; a moved HEAD is reset to the recorded head".

Every phase that changes the tree ends with the tree recorded:

- A fixer's answer, when recorded, is followed in the same append by
  one `tree.revised@1` per finding from `revisionsFromSnapshots` over
  its cluster's files plus every file the answer names (edited or
  created, under any finding), each with `source: { kind: 'fix', phase,
  key, workerId }`, `change: { findings: [ids], message }` and the
  finding's message (for a repair unit the ids are check kinds and the
  message is the repair worker's); nothing is appended for a cluster
  that changed no file. An owned file that differs and that no finding
  of the answer names fails the answer as a structural check (below),
  before anything is appended.
- A check that ran is followed by `tree.revised@1` with `source: { kind:
  'check', phase, check: kind }`, `change: { findings: [], message }`
  with a message the engine composes (`chore: apply the <kind> check's
  rewrite` and a body naming the command and the run), over the whole
  expected tree, when any file differs; a check killed with the engine
  leaves its writes for the re-entered phase's start check to find,
  which is the accepted edge.

### Snapshots (R6, PD14)

`deep-review snapshot --finding <n> --into <dir>` is a fourth
subcommand, run by a fixer from the worktree after each finding. It
lists the paths git reports as changed against `HEAD` (`git status
--porcelain=v1 -uall -z`, ignored files excluded) plus every scope path,
copies each that exists into `<dir>/<n>/<path>` as bytes (a symlink as
its target text, as the scope freezes it), and writes
`<dir>/<n>.json`: the listing with each path's SHA-256 and size, or
`absent`. It refuses an `<into>` that is inside the worktree, so a
snapshot can never be a stray. `<dir>` is `<scratch>/snapshots`, which
the phases module fixes by giving the invocation its `scratch` (the
launcher already accepts one) so the task text can quote the command
with the bundle's own path, as the skill texts do. A snapshot taken
twice for one index replaces the first.

The launcher removes nothing under the scratch while the engine runs,
and the controller reads the snapshots when it records the answer and
only then; the directory is the worker's and is not evidence, since
every byte the engine keeps from it is frozen into a revision.

### Ownership (R4)

A cluster owns its `files`. For the fixer's task the engine also lists
the files every other cluster of the phase owns, in cluster order. The
answer's files are normalized with the same `matchRepositoryPath` the
locations use, in the worktree's spelling; a reported path that names
nothing the worktree holds is kept as spelled when it is repository
relative and inside the worktree after `canonicalPath`, and refused as
a structural check when it is not (absolute outside the tree, `..`, or
under `.git`). A reported path that another cluster of the phase owns
is a violation: the answer is still recorded, the path is listed under
`violations` on `fix.recorded@1`, the file is revised like any other
and the report names it under Limitations with both clusters. The
repair unit owns every path the fixes phase's revisions name, created
files included; being its phase's only unit it can commit no violation,
and any other file it edits is reported and revised as a fixer's is.

### Policy (R12)

`roles/policy.json` gains:

```json
"fixer": { "tier": "strong", "effort": "high", "budgetUsd": 8, "timeoutMs": 1200000 },
...
"checks": { "timeoutMs": 1200000 }
```

- `resolvePolicy` requires the roles the engine runs, now `reviewRoles`
  plus `fixer` (fifteen), and the `checks` block, whose `timeoutMs` is
  1000 to 3600000 like a role's. The fixer's tier and effort are the
  proof of concept's (role prompts, D6); its timeout is twice a reader's
  because its prompt asks it to run the suite against the unfixed code,
  the fixed code and a mutation, and the checks' timeout matches it. The
  gate measures both (Open Questions).
- `review.configured@2` adds `fix: boolean` and `checks: { timeoutMs }`
  to v1's payload, and pins the fixer's role like the others. The v1
  reducer folds with `fix: false` and no checks block. The
  `configuration` on the fold gains the same two fields.
- Access and shell stay in code: `invocationFor` gives `access: 'edit'`
  to a `fixes` or `repair` unit and `read-only` to every other, `shell:
  true` to all. A policy column for access was rejected (TD7).

### Checks (R8, R9, R10)

**Discovery**, `src/review/checks/discover.ts`, pure over a snapshot of
the repository root the controller reads once (`package.json`, the lock
files, `Taskfile.yml`, `Taskfile.yaml`, `Makefile`, `justfile`,
`go.mod`, `Cargo.toml`, `pyproject.toml`, `pytest.ini`, and the `.sln`
and `.csproj` entries of the root) and the flags. For each kind, the
first source that has it wins:

1. `--check <kind>=<command>`, origin `flag`.
2. A Taskfile task, a Makefile target or a justfile recipe named
   `<kind>`: `task <kind>`, `make <kind>`, `just <kind>`; origin
   `taskfile`, `makefile`, `justfile`. Matching is a line at the start
   of the file's task, target or recipe position, as the proof of
   concept matched, with no YAML or make parser.
3. A `package.json` script, origin `package`: the first script present
   among the kind's names, `build`; `typecheck`, `type-check`,
   `check-types`, `tsc`; `lint`; `test`. When a script `<name>:check`
   exists beside `<name>`, `<name>:check` is taken (TD5). The command is
   `<manager> run <script>`, the manager being the `packageManager`
   field's name when present, else the lock file: `pnpm-lock.yaml`,
   `yarn.lock`, `bun.lock` or `bun.lockb`, `package-lock.json` or
   `npm-shrinkwrap.json`; none means `npm`; two lock files with no
   `packageManager` field refuse the configuration, naming them and the
   `--check` flag, before any run is created.
4. A language default, origin `language`: `go.mod` gives `go build
   ./...`, `go vet ./...` and `go test ./...`; `Cargo.toml` gives `cargo
   build --workspace`, `cargo check --workspace`, `cargo clippy
   --workspace` and `cargo test --workspace`; `pyproject.toml` or
   `pytest.ini` gives `python -m pytest` for `test`; a `.sln` or
   `.csproj` at the root gives `dotnet build` and `dotnet test
   --no-build`.

A kind with no source is recorded with `command: null` and origin
`none`; `--no-check <kind>` records `none` with origin `flag` and the
reason. The result is appended once as `checks.planned@1`
`{ checks: [{ kind, command, origin, reason }], manager }` at the
baseline phase's first attempt, and the fixer's task quotes the
commands. A run with no available check still runs the fix pass; the
fixers are told "no check is available" and the report says so.

**Execution**, `src/review/checks/run.ts`: a check is `runProcess` with
the platform shell as the executable, `cmd.exe /d /s /c "<command>"` on
Windows (with the argument passed verbatim) and `/bin/sh -c <command>`
elsewhere, `cwd` the worktree, stdin bound to an empty file, stdout and
stderr to files under `<checkpoint>/io/check-<id>/` that are frozen
afterwards as the workers' are, the timeout from the pinned policy, and
the environment `workerEnvironment(process.env, null)` plus `CI=true`,
`NO_COLOR=1`, `FORCE_COLOR=0`, `TERM=dumb`, `GIT_TERMINAL_PROMPT=0`. The
result is `check.ran@1` `{ phase, attempt, kind, command, outcome:
'passed' | 'failed' | 'timeout' | 'not-started' | 'skipped', exitCode,
signal, termination, startedAt, endedAt, stdout, stderr, error }`;
`passed` is an exit code of 0 after `exited`, `error` holds the spawn
failure of a `not-started` check, the tree-kill failure of a `timeout`
one, or the reason of a `skipped` one, and is null otherwise.

**Order.** In a checks phase the planner's `run-check` step names the
next check of the pinned list, in the order `build`, `typecheck`,
`lint`, `test`, that has no `check.ran` in this phase's attempt and is
available, and only one at a time; `typecheck`, `lint` and `test` are
each recorded `skipped` in `check.ran@1` with the reason "build failed"
when the build's outcome in this attempt is not `passed`, and are never
run then. The three do not wait on each other's outcomes (PD7). A
re-entered checks phase runs only the checks the earlier attempt did
not record.

**Baseline and repair trigger.** `checkOutcomes(fix, phase)` on the
fold gives each kind's last outcome in a phase. The repair phase has a
unit when some kind is `passed` in `baseline-checks` and `failed` or
`timeout` in `checks`; the report's Checks section shows the three
phases side by side, and a kind that failed at baseline is marked
"failing before the fix pass".

### Prompts and tasks (R4, R11)

`src/review/tasks.ts` gains two task texts, each ending "Return only
the JSON your schema describes":

| Role and unit | Task inputs | Task text says |
|---|---|---|
| fixer, `fixes:c<n>` | scope; the cluster's findings numbered `[0]`.. with id, severity, verdict (and `unverified`), angle, location (canonical, or the raw spelling marked unlocated, or "outside the change"), summary, detail, the verifier's evidence and merge-rank's reason; the owned files; the files other clusters own; the checks; the snapshot command with its `--into` path; whether the tree may already hold work | apply the findings in order under the role's rules; edit owned files and any file no cluster owns, never a file another cluster owns; after finishing each finding and before starting the next, run the snapshot command with that finding's index; report every file edited or created under the finding it served, with a commit message for each applied finding in the style `git log` shows; run the checks given; write logs under the scratch directory; when told the tree may hold earlier work, verify each finding against the code before applying it |
| fixer, `repair:repair` | scope; the failing checks numbered `[0]`.. with kind, command, exit code, the last 16 KiB of stdout and stderr inline and the frozen logs' paths; the owned files (every path the fixes phase revised); every fixer's answer, one line per finding with status and note; the checks; the snapshot command | make each failing check pass without undoing an applied fix, snapshotting after each; a check is `applied` when it passes, `deferred` with the reason when it cannot be made to pass here, `blocked` when it needs a file another rule forbids; same reporting rules, the message describing what the repair changed |

"The tree may already hold work" is stated when the unit's attempt is
greater than one, when the unit has a lost worker, or when a revision of
the phase names one of the cluster's files (an earlier answer's
violation). The scope block is element five's; the patch is the change
under review, not the fixers' edits, and the task says the worktree is
the current state.

The `Role:`, `Unit:` and `Phase:` header lines stay, so the fakes match
as they do today.

### Output schema and structural checks (R5)

`src/review/schemas.ts` gains `fixerOutput`, zod, strict and closed:

```
{ findings: [{ index (int ≥ 0),
               status: 'applied' | 'already-applied' | 'deferred' | 'blocked',
               file (1..1000), line (int ≥ 1 | null),
               note (1..400),
               message: { subject (1..72), body (0..2000) } | null,
               files: string[] (≤ 200, each 1..1000),
               corrections: [{ file, anchor, claim, fact, evidence }] (each ≤ 400),
               validation: [{ method: 'old-code' | 'mutation' | 'static' | 'existing' | 'limited',
                              source (1..400), evidence (1..1000) }],
               requiredFiles: string[] }],
  drift: [{ file, what (1..400) }],
  tests: [{ file, covers (1..400) }],
  suite: { result: 'pass' | 'fail' | 'not-run', command (0..400), failures (0..2000) } }
```

Structural checks, a failure being an `attempt.failed` like a schema
rejection: every index of the task appears exactly once; `message` is
present exactly when the status is `applied`, with a subject that has
no trailing period and no newline; `requiredFiles` is non-empty only
on a `blocked` finding and names no owned file; every reported path is
repository relative and inside the
worktree; every owned file whose bytes differ from the expected state
appears in some finding's `files`. The last check reads the tree, so it
runs where the controller records the answer, before the revision is
built from the same reading.

A retry after a structural failure is a fresh fixer told the tree may
hold earlier work. The `fixer-report.md` fragment lists these fields in
prose and nothing else (Prompt fragments).

### Retries, budget and blockers (R12)

The retry rule is element five's, unchanged: a unit with fewer than two
failures and no answer is launched; a cluster whose two failures hold no
lost worker degrades with `cluster.failed@1` `{ phase, key, reason }`,
which marks its findings "not attempted"; a lost worker among them
blocks with `worker-failed`. The budget check counts fixers like every
worker; checks cost nothing and are not workers. No blocker code is
added: a failing check is an outcome the report shows, a violation is a
mark, a stray is a list, and the fix pass reaches the report in every
case but drift, budget and `worker-failed`.

### Ledger events and fold (R6, R10 of element five)

New kinds, all version 1, with reducers in `src/checkpoint/fix-fold.ts`
registered beside the review reducers; the fixture `schema-1-05` is
committed with them:

| Kind | Payload | Reducer effect |
|---|---|---|
| `fixes.planned` | routes `[{ id, route: 'fixer' \| 'held' }]`, clusters `[{ id, findingIds, files }]` | `fix.plan`; once, in the fixes phase; every ranked id routed once; no file in two clusters |
| `checks.planned` | checks `[{ kind, command \| null, origin, reason \| null }]`, manager `\| null` | `fix.checks.planned`; once, in the baseline phase |
| `check.ran` | phase (a checks phase), attempt, kind, command, outcome (`passed`, `failed`, `timeout`, `not-started`, `skipped`), exitCode, signal, termination, startedAt, endedAt, stdout ref, stderr ref, error \| null | appended to `fix.checks.runs[phase]`; the phase must be running at that attempt; one run per kind per attempt |
| `fix.recorded` | phase (`fixes` \| `repair`), key, workerId, findings `[{ id \| kind, status, file, line, note, files, corrections, validation, requiredFiles }]`, drift, tests, suite, violations `string[]` | `fix.answers[phase][key]`; marks the unit answered; every finding of the cluster once |
| `tree.revised` | phase, source (`{ kind: 'fix', key, workerId }` \| `{ kind: 'check', check }`), change `{ findings: string[], message: { subject, body } }`, files `[{ path, status, after }]` (≥ 1, ≤ 2000) | appended to `fix.revisions`; the phase must be running; a fix source's findings name recorded ids of its unit, a check source's are empty |

Version 2 of the events that carry a phase, each a copy of v1 with the
wider `phase` enum and, for `worktree.checked`, the fields named above,
and for `review.configured`, `fix` and `checks`; the v1 schemas and
reducers stay as they are and fold into the same state: `phase.started@2`,
`phase.finished@2`, `worktree.checked@2`, `attempt.failed@2`,
`worker.lost@2`, `review.configured@2`, `report.written@2` (its
statistics rows). The engine writes only the v2 kinds. The
`reviewVocabularyV2` constant freezes the fourteen phases, the three
recorded codes, the check kinds and outcomes, the fix statuses, the
validation methods and the cluster id spelling `c<n>`; the vocabulary
test holds v2 equal to the live vocabulary and v1 equal to its own
frozen copy.

`ReviewState.phases` is keyed by the fourteen phases, with `skipped`
for the five fix phases of a run without `fix`. `ReviewState.fix:
FixState | null` is non-null once `fixes.planned` or `checks.planned`
is folded, with `plan`, `checks: { planned, runs }`, `answers`,

The four older fixtures fold with `fix: null` and every fix phase

one fix run through every new kind: a held finding, two clusters, a
violation, a stray, a check that writes, a failing check at baseline, a

### Planner steps

`nextStep` gains, in this precedence relative to element five's:

- After `plan-verification`: `plan-checks` (baseline phase, no plan yet)
  and `plan-fixes` (fixes phase, no plan yet).
- Before `degrade`: `run-check` in a checks phase, when no check is
  running and one is due; the controller runs it, appends `check.ran@1`

- Before `finish-phase` in `fixes` and `repair`: `check-worktree` with

`Live` gains `checkRunning: boolean` so a checks phase awaits a running

### Report and status (R13)

`renderReport` gains, after Findings and before Refuted at verification,
when `fix` is configured:

- **Fixes**: every ranked finding in rank order as `### <n>. <id>
  <status>`, where the status is `applied`, `already applied`,
  `deferred`, `blocked`, `not attempted (<reason>)` or `held for the
  author`, with the fixer's note, its corrections and, for a blocked
  finding, the files it needed; then a line per drift entry and per
  test the fixers reported.
- **Checks**: one table, a row per kind and a column per checks phase
  that ran (baseline, after fixes, after repair), each cell the outcome
  and seconds, a failing cell naming the frozen log's path; a kind not
  available names its origin `none` and reason; a kind failing at
  baseline is marked as such.
- **Changed files**: every path a revision names, once, with its final
  status (created, modified, deleted) and which clusters and checks
  revised it.

Limitations gains the violations (path, the cluster that reported it,
the cluster that owned it), the strays, and the validation and suite
lines the fixers returned. Statistics has a row for every fix phase;
the checks phases show seconds and no workers. The header says the run

### The patch series (R13, PD13)

`src/review/patch.ts` exports `renderPatch(before, after, paths):
string`, pure over two expected trees and the blobs they name: for
every path, one unified diff between its state before and after, in
path order, with git's own headers (`diff --git a/<path> b/<path>`,
`new file mode`, `deleted file mode`, and `Binary files differ` with
both hashes for a file that is not UTF-8 text or is frozen as hash and
size), so `git apply` reads it. The report phase renders one patch per
revision, in ledger order, `before` being the expected tree up to the
revision and `after` the tree with it, each prefixed by the revision's
message as a `git format-patch` mail header (`From`, `Subject`, the
body, `---`), stores each with `evidence.put`, and `report.written@2`
carries `patches: Ref[]`, empty for a run without `fix` or with no
revision. `status` and the report's header name them by number and
path, and the report's Fixes section names each finding's patch. The
command still prints only the report's path.

### The commit command (R17, PD13)

`deep-review commit [--run <id>] [--change-message <text>] [--repo
<dir>]` is a fifth subcommand, `src/review/commit.ts`, run after a fix
run on request:

1. Under the start lock and the run lock, fold the run: it must have a
   report, at least one revision and no `commits.created`; `--run`
   names one, else the newest such run of the repository is taken.
2. Refuse, naming the reason, when `git rev-parse HEAD` is not the
   scope's head; when any revised path in the worktree does not match
   its last revision (`compareExpected` over the revised paths, with no
   exclusion); when the scope's mode is `worktree` and
   `--change-message` is absent, or any other mode and it is present.
3. Build the commits with plumbing, each on the previous: for the
   captured change in `worktree` mode, the tree of the scope's head with
   every scope file set to its frozen after state (removed when `null`,
   added when the file was untracked), committed with the given message;
   then per revision, the previous tree with the revision's files set,
   committed with the revision's subject and body plus a trailer
   `Deep-review: run <id>, <ids> (<angle>, <verdict>)` for a finding
   revision and `Deep-review: run <id>, <kind> check` for a check's. The
   blobs are written with `git hash-object -w --stdin` from the evidence
   store (a symlink's blob as its target text with mode `120000`, an
   oversized file refused by name since its bytes were not frozen, which
   is a refusal before any object is written), the trees with `git
   mktree` from a listing the command composes, the commits with `git
   commit-tree`, so the author and committer are what git takes from the
   user's configuration and no hook runs. Nothing under the worktree is
   written; the objects go to the repository's object store.
4. Move the ref: `git update-ref <ref> <last> <from>` on the branch
   `HEAD` names, or on `HEAD` itself when detached, with the head the
   command started from as the expected old value, so a commit made
   meanwhile refuses the move and leaves the built objects unreferenced.
   Then `git reset -q` so the index equals the new head; a path the user
   had staged outside the revisions is left unstaged, not lost, and the
   command says so when it happens.
5. Append `commits.created@1` and print one line per commit: the short
   hash and the subject. Exit 0; 2 on a refusal with the reason; 1
   otherwise.

A second `commit` on the same run is refused by the ledger's record,
naming the commits. The command is the only place the engine writes to
the repository's git state, and it runs only when a person invokes it.

## Technical Decisions

- **TD1: Revisions are events beside the scope, not a re-captured
  scope.** Appending a second `scope.captured` was rejected: the scope is
  the change under review and its patch and base do not move when a
  fixer edits; a revision records what one worker or check left in the
  files it changed, and the expected tree is a fold over both. The fold
  refuses a second scope as before.
- **TD2: The worktree check in an editing phase runs at the start and
  the end, not per answer.** Element five checks before each answer is
  recorded because every worker of a phase must have read one tree. In
  an editing phase the tree changes by design, a fixer legitimately
  edits unowned files (its tests) that a sibling's per-answer check
  would flag, and the proof of concept's per-editor tree binding is
  what classified a deferring editor as drift because its siblings had
  edited. Excluding every unowned file too would leave nothing to check.
  The end check over the whole expected tree, once every answer has
  been revised in, catches what no answer accounted for; what it cannot
  catch is a user's edit to a file a fixer also edited, which is named
  in Risks.
- **TD3: Owned files of unanswered units are excluded from the start
  check too.** Without that, an interrupted fix run could never resume:
  the lost fixer's partial edits to its own files would be drift at
  re-entry. The replacement is told the tree may hold earlier work,
  which its prompt already handles as a success to verify.
- **TD4: Checks run through the platform shell.** `runProcess` refuses
  a shell so that no worker argument is reinterpreted, and the executable
  resolution refuses a `.cmd` shim because Node cannot spawn one. A
  check command is a string the repository wrote for a shell (`pnpm run
  -r --filter zod build`, `make test`), and the package managers are
  shims on Windows; running it through `cmd.exe /d /s /c` or `sh -c` as
  one verbatim argument is the honest execution, and the tree kill
  addresses the shell's tree as it addresses a worker's. Resolving each
  command's executable and refusing shims, as the proof of concept did,
  was rejected as a second executable-resolution rule with its own
  platform table.
- **TD5: `<name>:check` outranks `<name>` among package scripts.** The
  gate repository's `lint` script writes (`biome lint --write .`) and
  its `lint:check` does not, and the same pair is common (`format`,
  `format:check`). A script that writes is a fix, not a check, and
  taking the checking variant when the repository offers one costs one
  lookup. Revisited when a repository's `:check` script means something
  else.
- **TD6: A check's writes are a revision attributed to the check.** A
  formatter in `lint`, a generator in `build` and a snapshot updater in
  `test` all write expected files; treating that as drift would block
  every such repository, and reverting is a write by the engine (PD3).
  The revision names the check, and the report's Changed files shows it.
- **TD7: Access stays in code, not in the policy file.** A policy column
  for access was rejected: the phase decides what a worker may do, a
  policy that could give a reader `edit` would need a rule refusing it,
  and every role but the fixer is read-only by its nature. The pinned
  configuration records the roles' models and limits; the launch event
  records each worker's access.
- **TD8: One repair unit owning everything the fix phase changed.**
  Attributing each failure to a cluster from file names in the output
  was rejected: it needs the output parsed (PD8), and a broken build
  names no cluster. Re-dispatching every cluster with the log was
  rejected: parallel editors again, each unsure whether the failure is
  theirs. One worker that owns the union sees the whole result and
  reads the log as a person would; its cost is one strong-tier worker.
- **TD9: Skipped phases are in the fold, not absent.** A run without
  `fix` could have a shorter phase list, but two phase lists would put a
  branch in every fold invariant, the planner and the report. One list
  with five phases marked `skipped` at configuration keeps the invariant
  "every earlier phase finished" one rule.
- **TD10: The check runner reuses the worker environment and adds the
  non-interactive pins.** The build-server pins already exist for
  workers; `CI=true` makes vitest, jest and their kin run once instead
  of watching, and a bound empty stdin means a prompt reads EOF instead
  of waiting. The fixers' own environment gets no `CI` because the
  runtime CLIs read it.
- **TD12: The patches are rendered from frozen bytes, not from git.**
  A `git diff` of the tree after the run was rejected: in `--worktree`
  mode it holds the user's change too, and in every mode it holds
  whatever else moved in the tree. The run froze each revised path's
  state before and after every revision, so each diff is one change's
  work by construction; it costs one diff routine over blobs, which the
  series' `git am` test holds to git's format.
- **TD13: The commits are built with plumbing, not by applying patches
  through `git commit`.** Porcelain needs the worktree at each
  intermediate state, so the command would write every revised file
  once per finding and, in `worktree` mode, reverse-apply the fixes
  first; a crash mid-way would leave the tree in a state no revision
  describes. `hash-object`, `mktree` and `commit-tree` write only
  objects, the ref moves once at the end with a compare-and-swap, and
  the worktree already equals the last commit, so the command cannot
  leave the tree in a state it did not find it in. The price is that no
  hook runs, which `git am` shares, and which the command prints.
- **TD14: The snapshot is a command, and its listing is what git
  reports changed.** Asking the fixer to copy its files was rejected
  because a hand copy misses the test file it created in another
  directory; `git status` against `HEAD` lists every changed path
  whatever the mode, the scope paths are added so a path changed and
  changed back is still compared, and ignored files are left out as the
  revisions leave them out. The copy goes to the scratch, which both
  runtimes let a worker write, and never into the tree.
- **TD11: Findings, not files, are the unit of a fixer's report.** A
  per-finding `files` list, as the proof of concept's editor contract
  had, lets a deferred finding keep a partial edit without the engine
  losing which finding it belonged to, and the structural check that
  every changed owned file is on some finding is what makes the report
  truthful. A single top-level file list was rejected as losing that.

## Test Strategy

Fakes gain a `writes` and a `deletes` field on `ScriptStep`: files
(relative to the worktree, or under the scratch when prefixed) the fake
writes or removes before answering, so a scripted fixer edits the tree;
`defaultOutput` gives the fixer an answer that marks every index
`applied` with an empty file list. The review sandbox gains a
`package.json` whose `build`, `typecheck`, `lint` and `test` scripts run
small Node scripts that pass, fail, hang or write a file according to a
marker file the test controls, so a check's outcome is scripted without
a real toolchain; the sandbox has `package-lock.json` so discovery picks
`npm`. Every case runs on the three CI runners.

- Routing and clustering: each verdict and class routes as R2 says,
  `unverified` included; one cluster per file; a merged finding across
  two files merges two clusters and pulls every finding of both files
  in; an unlocated finding clusters alone by its raw spelling and owns
  nothing; two unlocated findings with one spelling in two cases share
  a cluster; cluster order follows rank; the plan is refused when a file
  is in two clusters or an id is routed twice.
- Expected tree: scope alone; a revision creating, modifying and
  deleting; two revisions of one path, the later winning; a revision on
  a path outside the scope; `compareExpected` with an exclusion set;
  `head` when HEAD moved; `reviseFrom` returning nothing for an
  unchanged path and hash-only entries above the cap.
- Discovery: a fixture directory per source (flag, Taskfile, Makefile,
  justfile, `package.json` with each lock file and with the
  `packageManager` field, `go.mod`, `Cargo.toml`, `pyproject.toml`,
  `.sln`), each kind's alias list, the `:check` preference, two lock
  files refused before a run exists, `--no-check`, and a repository with
  nothing giving four `none` entries.
- Execution: a passing, failing, hanging (killed with its tree, proven
  by a grandchild) and unstartable check on each platform through the
  shell; the environment pins present in the child; stdin at EOF; a
  check that writes a file yields a revision attributed to it; the
  chain skips the other three when `build` fails and runs all three
  when `build` passes or is absent; a re-entered checks phase runs only
  the missing kinds.
- Schema and structural checks: each field's bounds; a missing or
  repeated index; `requiredFiles` on an applied finding; a path outside
  the worktree; an owned file changed and unreported fails the answer
  and the retry's task says the tree may hold earlier work; a reported
  path owned by another cluster is a violation on the recorded event
  and a revision.
- Planner: synthetic folds for every new step in precedence; skipped
  phases passed over on a run without `fix`; the repair phase having a
  unit only when a baseline-passed kind failed; the end check of an
  editing phase awaiting the last unit; `checkRunning` awaited.
- Controller through the fakes, on each fake runtime: a full fix run
  reaches a report with the expected phases, a fixer's writes revised
  and shown under Changed files; a held design finding never reaches a
  fixer's prompt; two clusters run at once with disjoint files; a fixer
  that edits an unowned scope file and reports it revises it without
  drift; one that edits a sibling's file and reports it records a
  violation and the run completes; one that edits a sibling's file
  without reporting it (a scope file) blocks the phase's end check with
  `drift` naming the file and its expected evidence path, and restoring
  the file and running again completes; a stray file is listed, not
  blocking; a check failing at baseline is reported and not repaired; a
  fixer that breaks `test` triggers one repair whose fixer fixes it and
  the repair checks pass; a repair that fails leaves the check failing
  in the report and the run complete; killing the engine while a fixer
  runs and running again resumes without drift on the lost fixer's
  owned files, and the fresh fixer's task says the tree may hold earlier
  work; a user commit during the fix phase blocks with the head named;
  a fixer failing twice degrades the cluster to "not attempted" and the
  report says so; a Codex fake reaches a fix report with no budget.
- Events and fold: every new reducer's invalid histories (a second
  plan, a run for a phase not running, two runs of one kind in an
  attempt, an answer for an unknown cluster, a revision with no files);
  v1 and v2 of each versioned kind fold to one state; the four older
  fixtures fold with `fix: null` and five skipped phases; `schema-1-05`
  folds to its recorded state; the golden test refuses the registry
  change without it.
- Vocabulary: v1 equal to its frozen copy, v2 equal to the live one.
- Blockers: the enumeration test element five described and does not
  have: every code in `blockerCodes` has a non-empty action, every
  recorded code survives `status --json`, and the drift action names
  the evidence path and the head.
- Report: the snapshot extended with the three sections, the patch line
  in the header and the new Limitations lines; a run without `fix`
  renders as before.
- Snapshots: the command copies a modified, a created and a deleted
  path (listed `absent`), a symlink as its target, and a scope path
  changed back; an ignored file is left out; `--into` inside the
  worktree is refused; a second snapshot of one index replaces the
  first; `revisionsFromSnapshots` on a cluster of three findings with
  all snapshots gives three revisions, with the middle one missing
  gives two naming three ids, with none gives one from the worktree,
  and with a snapshot that changed nothing folds it forward.
- Patches: a created, a modified, a deleted, a CRLF, a non-UTF-8 and an
  oversized file; one patch per revision in ledger order with the
  message header; a run with no revision has none; on each platform the
  series applies with `git am` to a fresh checkout at the scope's head
  and the resulting tree equals the final revisions byte for byte, with
  the user's uncommitted change left out of it in a worktree-mode
  sandbox.
- Commit command: on each platform, after a scripted fix run, the
  command creates one commit per revision whose trees `git diff-tree`
  shows touching exactly the revision's paths, the last tree equal to
  the worktree, the index clean afterwards, the author from the sandbox
  repository's `user.name` and `user.email`, no `pre-commit` hook
  invoked (a hook that writes a marker is installed and the marker is
  absent), and `commits.created@1` on the ledger; in worktree mode the
  captured change is the first commit with `--change-message`, refused
  without it, and the flag refused in last-commit mode; refusals for a
  moved HEAD, a revised file edited after the run, a run without a
  report, a second invocation, an oversized revised file and a detached
  HEAD moved in place; a staged path outside the revisions is unstaged
  and named; a commit made between the fold and the ref update refuses
  the move and leaves the ref where it was.
- Policy: the committed file resolves with fifteen roles and the checks
  block; a policy without `fixer` or `checks` is refused; the digest
  changes when a fixer fragment changes.
- Command line: `--fix` without a scope refused as before; `--check`

## Risks & Migration

- Risk: a user's edit to a file a fixer also edits during the fixes
  phase is attributed to the fixer, since the end check sees the
  fixer's revision cover it. Accepted (TD2); the fixer's answer names
  what it changed, and the report's Changed files is where the user
  looks first.
- Risk: the end check of an editing phase blocks on a legitimate edit a
  fixer made to an unowned expected file and did not report, and the
  operator's only actions are to restore that file or abandon.
  Accepted; the fixer's prompt says to report every file, the block
  names the file and the bytes, and the Open Questions keep an adopt
  action for the evidence.
- Risk: a check killed with the engine leaves a partial write that the
  re-entered phase's start check reports as drift. Accepted; the block
  names the file and its expected bytes, and the case needs a hard kill
  during a writing check.
- Risk: the shell command a manifest names may itself spawn a watcher
  or a daemon that the tree kill misses on re-parenting. Accepted, as
  the runtime adapter accepted it for workers; the build-server pins
  cover the known case and `CI=true` the common watchers.
- Risk: `cmd.exe /d /s /c` quoting differs from what the user's own
  shell does with the same command, so a command that works in
  PowerShell may not run. Accepted; the command's exact string and
  its output are evidence, and `--check` names one that does.
- Risk: the version 2 events double the review vocabulary's frozen
  copies, and a third widening will need a version 3. Accepted; that is
  the rule AGENTS.md sets, and each copy is a few lines.
- Risk: the fixers' frozen prompts hold the ranked list and every
  cluster's task, and the repair's holds every answer and 16 KiB per
  failing check, so the evidence store grows by a few hundred kilobytes
  per fix run beyond the read-only run's. Accepted, as element five
  accepted the inline patch.
- Migration: none for existing checkpoints. Every new kind is version
  1, the older versions stay registered with their reducers, the four
  fixtures fold as before, and a run recorded by an older engine shows
  `fix: null` and five skipped phases in `status`.
- Migration for installs: the next `plugin marketplace update` or
  directory copy brings the flag; a user who passes `--fix` to an older
  bundle gets its usage error, which names no such flag.
