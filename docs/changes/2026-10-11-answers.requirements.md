# Product Requirements: Answers

Technical part: [2026-10-11-answers.design.md](2026-10-11-answers.design.md).

## Summary

A person answers a question the decision step asked, or accepts or
rejects a departure a fix made from a rule, with one command,
`deep-review answer`, after the run has written its report. The answer
goes on the run's ledger as a fact before anything is edited. On a run
that fixed, the engine then sends that finding alone back through a
fixer: the fixer makes the tree hold what the person decided, the
option chosen in place of the default the run applied, or the rule the
rejected departure left, and the checks run again; `deep-review
commit` then commits that work on top of the commits the run already
made. On a run that only reviewed, the answer is recorded and the
continuation into the fix pass applies it with the other fixes. Today
an ask is answered by a default and nothing can be said back to the
engine: the recommended option, which differed from the applied
default in 17 of the 21 questions this repository's runs asked, is lost
unless a person does the work by hand, and nothing records what the
person decided.

One thing the vision asks of an answer is not built here: the engine
does not turn the answer into a rule the next review reads, so the
same question may be asked again. The fixer that applies an answer is
free to amend a statement of the behavior as part of holding the
answer, as any fixer is; nothing requires it, places it or reads it
back (PD3).

This is the second item of the plan reoriented on 2026-10-10 and the
first element written against the vision note of 2026-10-11. It
implements principles 3, 7 and 10 of that note, a departure is accepted
or rejected, the answer comes later and fixes only its finding, and the
answer is a label; it records what principles 4 and 9, asked once and
rules grow from answers, later build on, and departs from them until
then.

## Problem

The decision step decides every ranked finding before any fixer runs:
`fix`, `leave`, or `ask`. An ask carries a question, two to four
options each with its cost and the rule a convention source would state
for it, the option recommended, and the option applied, which is the
one easiest to take back (decision step, R3, R4). The run never waits:
a fixer applies the default when it edits the code, and the report
lists the question as a checklist item for the author (R8). The
decision step left two things out on purpose (its Non-Goals): a memory
of answers, and an `answer` command that records the author's answer
and fixes that finding again.

What the runs since then show, read off this repository's own ledger on
2026-10-11:

| | |
|---|---|
| Runs with a decision step | 11 |
| Decisions | 243 |
| Questions asked | 21 |
| Questions whose default keeps the code | 17 |
| Questions whose default edits the code | 4 |
| Questions whose recommended option is not the applied one | 17 |
| Fixes that depart from a rule | 11 |

- **The recommended option is lost.** In 17 of 21 questions the decider
  recommended an option other than the default it applied. The default
  is the right thing to apply unasked, by R4 of the decision step; but
  there is no way to say "take the recommended one", so the question's
  answer is whatever the person does by hand after reading the report.
  In the one case so far where the author answered, RIPPLE-3 of the
  continuation gate (run `9b0f59a4`), the author rewrote the
  requirement by hand (`528aa8b`), and the engine knows nothing of it.
- **Nothing records the answer.** The overturn rate the decision step
  defined as a metric, the share of decisions an author reverses, is
  still unmeasurable: nothing records an answer, so no answer is a
  label (vision, principle 10).
- **The rule is not written.** Each option carries the rule a convention
  source would state for it, written so that the next review settles
  the question alone (decision step, R3; vision, principle 9). It is
  printed in the report and goes nowhere. A question the person answers
  by editing the code is asked again by the next review of a change
  that touches the same question. This element records the answer and
  builds nothing that writes or reads a rule from it (PD3); the record
  is what a later element turns into one.
- **A departure cannot be reviewed.** A fix that departs from a rule
  names the rule, its source and the reason, and amends what states the
  rule (decision step, R5). The vision gives the person three choices
  on a departure: accept, reject, or do nothing (principle 3). Only the
  third exists.
- **After `commit` the run is closed.** Every worktree check compares
  `HEAD` with the scope's head, and `deep-review commit` refuses a run
  whose `HEAD` is not the scope's head (`refuse` in
  `src/review/commit.ts`). Once the series is committed, `HEAD` is the
  series' last commit, so no worker can run on the run again. An answer
  that arrives after the commits, which is when a person reads a pull
  request, has no run to act on. The plan's third item, questions
  answered on the pull request, cannot exist without this.

What the questions were about says how hard the rule is to place. Every
one of the 21 is a question about the engine's own behavior: which run
`commit` picks with no `--run`, whether a check's revision takes a file
the check created, whether the skills pass `--fresh`. The rule text of
each option is a sentence of product behavior, and the places the
decider looked are the change proposals under `docs/changes/` and the
docstrings beside the code, not `AGENTS.md`. The one answer given by
hand went into the proposal that states the behavior. The plan item
names "`AGENTS.md` or the file the survey found" as the rule's home;
that is the wrong default for this repository, and would be for a
library whose questions are about its own semantics. The rule belongs
where the repository states the behavior the question is about, which
file that is takes judgment, and whether the next decider finds it
there is a second judgment that can only be measured. That is why this
element builds nothing that writes or reads the rule, and leaves the
fixer's own judgment about amending a statement alone (PD3).

## Goals

- A person answers a question, or reviews a departure, with one command
  that needs nothing but the finding's id and the option's number as
  the report prints them, and the answer is on the ledger before any
  edit.
- An answer on a run that fixed is applied by one fixer to that finding
  alone: the tree comes to hold what the person decided, the checks
  run again, and the work can be committed on top of the run's commits.
- An answer on a run that only reviewed is applied by the continuation
  into the fix pass, with no second review.
- Every answer, accepted departure and rejected departure is a recorded
  fact a later measurement can read as a label.
- An older engine still reads every ledger it could read before, and
  this engine reads every ledger written before it.

## Non-Goals

- **No mechanism turns the answer into a rule, and the next review may
  ask again.** The vision says an answer becomes a rule and a question
  is asked once (principles 4 and 9). Deriving the rule from the
  answer, placing it where the next decider looks, and proving that the
  decider then decides without asking are each a judgment, and
  together more than this element takes on; the decision step's own
  survey of where rules live (above) says the place is not a fixed
  file. The engine therefore builds no step that writes a rule, no
  instruction to the fixer about where one goes, and no reader of one;
  the answer stays on the ledger, where a later element reads it to
  write and measure the rule (PD3). The fixer that applies an answer
  may amend a statement of the behavior if holding the answer calls for
  it, as any fixer may, and is neither told to nor told not to. Until a
  mechanism exists, the first review of a change that touches the same
  question may ask it again, and the report says so.
- **No free-text answer.** An answer is one of the options the ask
  gave, or accept or reject on a departure. An option the decider did
  not offer has no cost written for it, and would need a decider's turn
  to get one; the person who wants it edits the code by hand (PD8).
  Revisit when answers show the need.
- **No answer to a `leave` or to a `fix` without a departure.** A leave
  cites a reason, and a person who disagrees with an `intended` leave
  disagrees with the rule it cites: the vision's answer is that the
  person changes the rule (principle 4), which a convention source edit
  does without the engine. A fix without a departure is the engine's
  own decision on a question the repository answers; overruling it is
  editing the code (PD9).
- **No re-fix on a tree that moved.** When `HEAD` is not at the run's
  head, the scope's or the last commit the engine made, the answer is
  recorded and the re-fix is refused naming what moved and the option
  chosen, for the person to carry (R6). Reviewing a changed tree from
  the last run's verdicts is the plan's seventh item.
- **No repair in the answer pass.** The pass runs one fixer and the
  checks; a check that fails after it is reported, as the fix pass
  reports one its repair could not mend. A repair for an answer is
  built when a run shows the need (principle 11).
- **No change to the decider's rubric or output.** The ask's shape,
  `decisions.recorded@1`, is unchanged. The change the decision step's
  gate suggested, a `fix` whose approach makes no edit treated as a
  leave, is a rubric change that is measured before it lands and is not
  made here (PD10).
- **No pull request surface.** The command is the one surface; the
  plan's third item posts questions as review threads and reads replies
  as answers through this command.
- **No corpus work.** The answer event is what the plan's ninth item
  reads as a label; nothing here scores a rubric against it.
- **No `by` on the answer.** Who answered is not recorded; the pull
  request surface adds a version of the event with the account that
  replied, when it needs one.
- **No severity floor.** Deferred as before.
- **No runtime-specific behavior.** `answer` runs the pass on the
  runtime the run pinned, as a resumed run does; nothing in the pass
  branches on the runtime, and the Codex gate (R13) is the proof, not a
  second code path.

## Requirements

- **R1: `deep-review answer` records one answer on the ledger.** The
  command takes `--finding <id>`, the finding's id as the report prints
  it, and one of `--option <n>`, the option's number as the report
  numbers it from 1, `--accept` or `--reject`; optionally `--note
  <text>`, `--run <id>`, `--record-only`, `--budget-usd <usd>`, `--roles
  <dir>` and `--repo <dir>`. It appends one `answer.recorded` event to
  the run, naming the finding, the answer and the note, before anything
  else happens. The event is appended under the run's lock, after the
  run is read again under it, as every writer of a run does. The answer
  is one of three kinds, `option`, `accept` and `reject`, and every
  reader of an answer branches on the kind (PD2).
- **R2: Which run.** With no `--run`, the run is the newest complete run
  of this worktree that was configured with the decision step, by its
  last event in the ledger; `--run` names another. A run that is
  active, blocked or abandoned, one of another worktree, one configured
  before the decision step, or one this engine cannot read is refused
  with the reason, exit 2; a run with no `--run` when none qualifies is
  refused naming `--run`. A finding the run's ranking does not hold is
  refused naming the run and the ids that can be answered on it.
- **R3: What can be answered.** `--option <n>` answers a finding decided
  `ask`, with `n` among its options; `--accept` and `--reject` answer a
  finding decided `fix` with a departure. Anything else, a `leave`, a
  `fix` without a departure, `--option` on a departure, `--accept` on an
  ask, or `n` past the options, is refused with the finding's decision
  and what it admits. A finding may be answered again; the last
  recorded answer stands, and an answer equal to the standing one is
  refused as already given, unless it still owes an edit on a run that
  fixed: it is then not recorded again, and the pass that applies it is
  opened, which is how an answer whose pass R6 refused is applied once
  the tree or the budget allows. An answer that names what the tree already
  holds, the applied default, the option an earlier answer applied, or
  the departure as the fix made it, confirms it: it is recorded and
  owes no edit, so no fixer runs for it (PD12). An answer that names
  something else, another option or the rule a departure left, owes an
  edit.
- **R4: On a run that only reviewed, the continuation applies the
  answer.** A complete read-only run keeps its report; `answer` records
  the answer and says that `review --fix` applies it. The continuation
  (fix pass continuation, R1) then routes every finding whose answer
  owes an edit to a fixer, whatever its decision's default did, and
  that fixer is told the answer: for an option, the option chosen, its
  text and the note; for a rejected departure, that the fix follows the
  rule as its source states it. The fixer makes the tree hold what the
  answer says (R7). A finding whose answer owes no edit routes as its
  decision does: a confirmed default as today, an accepted departure to
  the fixer that makes the fix. A continuation that finds nothing to
  fix (fix pass continuation, R5) counts a finding whose answer owes an
  edit as one to fix. A continuation that does not qualify, because the
  change moved, creates a new run as today; the answers stay recorded
  on the old run, and the log says they do not carry.
- **R5: On a run that fixed, the answer pass applies the answer.** A
  complete fix run, continued or started with `--fix`, gets an answer
  pass unless `--record-only` is given: the engine appends one
  `answer.pass` event naming every answered finding whose standing
  answer owes an edit no fixer has made yet, which opens two phases,
  `answer` and `answer-checks`, and the report phase again; it then
  runs the run to its report in the foreground as `review` does, and
  exits as `review` exits. When no answer owes an edit the command
  records, says so, and exits 0 without a pass. The `answer` phase
  launches one fixer, edit access, told every finding of the pass as a
  fixer is told a finding (decision step, R7) and, for each, what the
  run did with it before (the fixer's status, note and the files of its
  revision, or that no fixer saw it), and the answer. The fixer owns
  every file the run's revisions changed and may edit any other, as the
  repair worker may, claims nothing, snapshots after each finding so
  each answer is one revision and one commit, and returns the fixer's
  schema. The `answer-checks` phase runs the run's planned checks again,
  as the `checks` phase runs them after the fixes, and a check that
  fails is reported. A fixer that fails twice blocks the run with
  `worker-failed`, as the decider does, since an answer is the person's
  act and nothing else waits; the run budget blocks the phase before a
  launch as it blocks a reading phase. A later `answer` after the pass's
  report opens another pass.
- **R6: The pass needs the tree where the run left it.** Before the pass
  is opened, `HEAD` must be the run's head: the scope's head, or when
  `deep-review commit` made commits for the run, the last commit of the
  last series it made; and every file the run expects must hold what
  the run recorded last, compared as git would store it. Otherwise the
  pass is refused, exit 2, the answer stays recorded, and the message
  names what moved and what the answer says, the option's text or the
  rejected departure's rule and source, so the person can apply it by
  hand; it says that a review of the changed tree is a new run, which
  does not carry the answer. A run whose spend reaches the run budget
  in force is refused before the pass, naming `--budget-usd`, as a
  continuation is. An interrupted pass is resumed by `review`, which
  resumes any active run; the answers recorded are then applied by the
  resumed pass.
- **R7: The fixer makes the tree hold what the answer says.** For an
  option, the fixer undoes the edit the default made, where it made
  one, and makes the edit the chosen option describes, within the
  finding's files and whatever else the option needs. For a rejected
  departure, it restores what stated the rule, which the departing fix
  amended, and makes the fix follow the rule as its source states it.
  An accepted departure owes nothing: the departing fix amended the
  rule's statement already. The fixer is told the option's text, or
  the departure's rule, source and reason, and nothing about writing a
  rule: whether holding the answer calls for amending a statement of
  the behavior is its judgment as on any finding, and the engine
  neither asks for it nor reads it (PD3). The commit message's body
  names the question and the answer.
- **R8: `deep-review commit` commits an answer pass on top of the run's
  commits.** A run whose revisions were committed and that then gained
  revisions in an answer pass is committable again: `commit` builds one
  commit per uncommitted revision, in ledger order, from the last
  commit it made for the run, refusing a `HEAD` that is not that
  commit, and records a second `commits.created`. In worktree mode the
  captured change is committed by the first series only. With no
  `--run`, `commit` picks the run that finished last among those with
  revisions no commit holds. A run never committed is committed as
  today.
- **R9: The ledger records answers and passes, and every older ledger
  still reads.** Two kinds: `answer.recorded@1`, the answer; and
  `answer.pass@1`, the pass and the findings it applies. Two phases,
  `answer` and `answer-checks`, after `repair-checks` and before
  `report`, skipped at every configuration and opened only by an
  `answer.pass`; the kinds that carry a phase gain a version that can
  name them. The fold holds every answer and every pass, the second
  report takes the first's place and the first stays beside it, as a
  continuation keeps its read-only report, and `commits` becomes a
  list. Every committed golden fixture and every recorded run of the
  replay corpus still opens and folds, and a new golden fixture holds
  an answered run.
- **R10: The report and `status` show the answers and how to give one.**
  Under Decisions, each question's checklist item is checked once
  answered, with the option chosen, when, and whether it was applied by
  a pass, by the fix pass, or owed no edit. Each unanswered question
  ends with the `answer` command that answers it, finding id and the
  options' numbers filled in, so a reader needs nothing else to answer;
  each departure says accepted or rejected, when, or ends with the
  command that reviews it. The section says once that an answer is
  recorded and applied to this run, and that nothing yet carries it to
  the next review, which may ask again. The header says how many
  answers the run holds and, after a pass, when the last pass ran and
  where the report before it is. Fixes shows the answer pass's outcome
  for each finding it worked, the Checks table gains the pass's column,
  and the patch series holds the pass's revisions after the run's.
  `status` prints the answers' counts and the passes, and `--json`
  carries them.
- **R11: The auditor leaves the role prompts.** The `auditor` role, its
  fragments `auditor-brief.md` and `step3-verdicts.md`, and the unused
  `answer` role of the manifest, whose fragments are the fixer's, are
  removed, since the audit they served was set aside and answers take
  its place; the fixer's prompt no longer promises a later adversarial
  pass over its defers. Each is its own commit, and the roles digest
  changes, so an active run resumes only with `--roles <dir>`.
- **R12: The skills and the README say it.** Both skill texts say that
  the report's Decisions section lists the questions and departures
  with the command that answers each, how to run it when the user
  answers one, what its exit codes mean, and that after answers on a
  read-only run the same command with `--fix` applies them. The skill
  texts change in their own commit. `README.md` gains a section on
  answers, says that an answer is applied to its run and recorded and
  that nothing yet carries it to the next review, and points at this
  proposal.
- **R13: The gate.** On this repository, on both runtimes, with no hand
  on the runs: the element's own change is reviewed read-only; one
  question is answered before `--fix` continues the run, choosing the
  recommended option when it is not the default (R4); after the fix
  pass and `deep-review commit`, another question is answered with an
  option that owes an edit, or a departure rejected, and the answer
  pass runs and is committed on top (R5, R8); `npm run check` and `npm
  run verify` pass at the head. The cycle runs first on Claude Code,
  then on Codex from a fresh clone of the same change, under the
  Windows sandbox the policy ships, which is the first fix run on Codex
  since the decision step and the full-scale run the sandbox choice's
  R10 asked for. Each cycle passes on its own terms: a report at every
  step with no hand on the run, and on Codex no fixer or repair result
  holding `spawn EPERM`. When the change's review asks no question on
  a runtime, the read-only path is taken on the newest finished run of
  that runtime in this worktree that asked one, and the pass path on a
  departure, which every dogfood run so far had. The design's
  Verification records both cycles' reports, the pass's spend and
  workers, and what each fixer did with the answer.
  (Amended 2026-10-13, decided by the author: the gate's change is an
  open-source pull request, not this element's own change. It is
  j178/prek #2724, a Rust change of 11 files whose repository states
  its rules in `AGENTS.md`, reviewed from its base to its head in a
  local clone, with nothing sent to the project. The checks that must
  pass at the head are the project's own, `cargo fmt --check`, `cargo
  clippy` with warnings denied, and the integration tests the change
  touches, in place of `npm run check` and `npm run verify`. A change
  someone else wrote is the use the element is for, and reviewing this
  element's own change would run the engine under test on its own
  sources, where a changed role prompt or a rebuilt `dist/` is part of
  the change. Its review asked one question and made no departure, so
  the pass path answers the same question again after the commit, with
  the default, which owes the edit that undoes the recommended option
  applied by the fix pass; the author chose this over a second
  open-source change.)

## Metrics

- **The cost of an answer.** The answer pass's spend and workers, from
  the report's Statistics, against the read-only review's: target one
  fixer and the checks, under 5 USD on this repository.
- **The overturn rate**, defined by the decision step and unmeasurable
  until now: the share of asks whose answer is not the applied default
  and of departures rejected, over all asks and departures of a run,
  read from the ledger. Recorded from this element on; no target yet.
- **Asked again** is not measured here: it measures a mechanism this
  element does not build, and belongs to the element that builds it
  (PD3).

## Product Decisions

- **PD1: The answer is a fact first; the re-fix needs the tree.** An
  answer is recorded whatever the tree holds, since it is the person's
  decision and the corpus's label (principle 10), and the re-fix is
  refused when the tree moved (R6). Refusing the answer itself when the
  tree moved was rejected: it would lose the label and make the person
  answer again later.
- **PD2: One command for questions and departures.** A departure is a
  question of the same shape: the decider stated a rule, departed from
  it for a reason, and the person's answer is one of the choices
  offered, accept or reject, as an option is one of the ask's. The
  vision treats the two alike as what becomes a rule and a label
  (principles 3, 9, 10), and the re-fix is the same frame: a fixer told
  what the run did and what the person decided. So the answer is one
  event with three kinds, `option`, `accept` and `reject`, taken by
  three flags on one command, and routed, applied, reported and labeled
  by code paths that branch on the kind. A second command for
  departures was rejected as two names for one act, and leaving
  departures to a later element was rejected for the same reason.
- **PD3: The engine builds nothing that derives a rule from the
  answer.** The plan item had the answer write the option's rule text
  into `AGENTS.md` or the file the survey found, so that the next
  review would not ask again; having the fixer place the rule where
  the repository states the behavior instead was considered and
  rejected with it. Deriving a rule from an answer, placing it where
  the next decider looks, and making that decider read it are each a
  judgment that has to be measured, and this repository's
  evidence says the place is not a fixed file: every question so far
  was about the engine's behavior, the decider looked in change
  proposals and docstrings, and the one rule written by hand went into
  a proposal. A rule in the wrong place is noise the next decider does
  not find, and a wrong rule is worse than a repeated question. The
  element records the answer as the label and the fact (principle 10),
  applies it to the tree, and leaves the mechanism to an element that
  can design and measure it on recorded answers. Not building the
  mechanism is not a ban: the fixer that holds an answer may amend a
  statement of the behavior when the edit calls for it, as any fixer
  may, and is told nothing either way, so the task does not steer that
  judgment. The report says the question may be asked again.
- **PD4: A read-only run's answers ride the continuation.** A pass on a
  read-only run would need the fix pass's pins, the checks and a
  survey, for one finding; the continuation already routes every
  finding by its decision and asks the surveyor for the checks once.
  So an answered finding routes to a fixer under the continuation and
  the fixer is told the answer (R4). The person's step is then
  `answer`, then `review --fix`, which the skill says.
- **PD5: One fixer for every unapplied answer, with no claims.** The
  pass runs alone: no other editor is in the tree, so the claims that
  keep fixers apart serve nothing, and one worker over two or three
  findings is one worker. One worker per answer was rejected as more
  launches for the same edits; running the pass inside the fixes
  phase as a third round was rejected because the claims, the rounds
  and the second-round plan are built for two rounds and the pass
  needs none of them.
- **PD6: Confirming what the tree holds runs no fixer.** An answer that
  names the option the tree already holds, or accepts a departure,
  changes no code, and with no rule the engine asks for (PD3) there is
  nothing for a fixer to do; it is recorded as applied by the tree.
  Running a fixer anyway, to have one revision per answer, was
  rejected as a launch that edits nothing.
- **PD7: After `commit`, the run's head is its last commit.** The
  worktree check and `commit` compare `HEAD` with the scope's head
  today, which closes a committed run. The run's head becomes the last
  commit the engine made for it, when it made one (R6, R8); the
  expected files are unchanged, since the commits are built from the
  same frozen bytes. Reopening the run by rewinding `HEAD` was rejected
  as a hand on the tree; copying the run was rejected by PD1 of the
  continuation.
- **PD8: Options only.** A free-text answer would carry no cost and
  would need a decider's turn to get one; the options are what the
  person can decide from the question alone (principle 6). A person who
  wants another option edits by hand; the report says so.
- **PD9: A leave and an undeparted fix are not answerable.** See
  Non-Goals. The population to overrule them is the audit's, which the
  plan set aside at 0 in seven runs; reopen with it.
- **PD10: The rubric does not change here.** The plan item bundles a
  rubric change, a `fix` with no edit read as a leave. The decision
  step's rule is that a rubric change is measured before it lands, and
  its gate found the case twice in two pytest runs and never since. It
  is its own small proposal, measured on the replay corpus, and not
  mixed into an engine change whose gate reads something else.
- **PD11: `answer` records and then runs; `--record-only` defers.** A
  command that only records, with `review` running the pass, was
  rejected: the pass would have to be opened at record time to make
  the run resumable, and a run left open that way would be resumed by
  the next `review` of another change in the worktree, which ignores
  scope flags for an active run. So `answer` opens the pass only when
  it is about to run it, and `--record-only` leaves the run complete
  for the next answer. An interrupted pass is resumed by `review`, as
  any active run is.
- **PD12: The answer may name what the tree holds.** See PD6. Refusing
  it as a no-op was rejected: it is an answer, and a label.
- **PD13: The gate runs on both runtimes.** The fix pass's two later
  elements were accepted on Claude Code alone, and no fix run has used
  Codex since the decision step, so the engine's editing path on Codex
  is several elements behind in practice: claims, the decision step,

## Against the vision note

Read against `docs/2026-10-11-vision.md`:

- Principle 2, record before action: the answer is on the ledger before
  the fixer launches (R1), and the pass before the phases open (R5).
- Principle 3, a departure is accepted, rejected or left: the three
  choices exist, with one command (R3, PD2).
- Principle 5 and 6, what reaches the person: the report's checklist
  gains the command that answers each question, so a person answers
  from the question alone (R10); nothing more is added to read.
- Principle 7, nothing waits: the pass fixes the answered findings only
  (R5), on a run that already reached its report; no question blocks.
- Principle 10, answers are labels: `answer.recorded` is the label (R9,
  PD1).
- Principle 12, a real run is the gate (R13).

Two departures, named:

- Principles 4 and 9, asked once and rules grow from answers: this
  element builds nothing that carries an answer to the next review, so
  the next review of a change touching the same question may ask it
  again (PD3). The reason is that deriving and placing the rule, and
  proving the next decider reads it, is its own element, to be designed
  on recorded answers; the answer event is the record it will read. A
  fixer that amends a statement while holding an answer narrows the gap
  on its own judgment, but nothing counts on it. The report tells the
  person that the question may come back.
- Principle 7, the answer fixes its finding: R6 leaves the answer to the
  person when the tree moved past the run. The reason is that a fixer
  on a tree the run does not know would edit without the expected tree
  the record rests on (principle 1); the plan's seventh item, review of
  a changed tree from the last run's verdicts, is where the answer
  follows the change.

## Risks

- Risk: the same question is asked again on the next change that
  touches it, and the person answers it again. Accepted by PD3; the
  two answers are two labels, and the element that writes rules reads
  them.
- Risk: the answer pass's fixer, owning every revised file and free to
  edit any other, undoes a sibling fix while applying an answer.
  Accepted: it is told what each fixer did and each finding is one
  revision the person reads; the checks run after it.
- Risk: a person edits the tree by hand between the commit and the
  answer, and the pass is refused for drift. Accepted: the refusal
  names the files and the option; the answer stays recorded.
- Risk: the run's head moving with its commits reaches every reader of
  the scope's head. Mitigated by one function the drift check and
  `commit` both call; the base state of a path outside the expected
  tree stays the scope's head's, since the commits change only expected
  paths.
- Risk: two reducers now move phases out of `skipped` or `completed`,
  the continuation's pin and the answer pass. Accepted: each is one
  event that says what it reopens, and `phaseStarted` keeps its rule.
- Risk: the roles digest changes with R11, so every active run must be
  resumed with `--roles <dir>` or started again; a finished read-only
  run under the old roles is continued only with `--roles` too (fix
  pass continuation, PD8). Accepted as at every prompt change.
- Risk: the gate change asks no question, or only one. Then R13 is
  taken on another open change whose review asks enough, which delays
  the gate but does not weaken it; 21 questions over 11 runs says a
  run that asks two is not rare.
- Risk: cost. One strong fixer and the checks per answer pass, under
  the fixer's 8 USD cap; measured at the gate.
- Risk: the Codex cycle fails on something older than this element,
  since claims, the decision step and the continuation have never run
  on Codex; its last fix run saw batches of up to 1125 s and fixers
  that could not start a process under the sandbox then shipped.
  Accepted, and the point of PD13: a failure there is a finding against
  the engine on Codex, recorded in the Verification with the run it
  came from, and is fixed before the element is accepted, in this
  proposal when it is the pass's and in its own when it is older.
