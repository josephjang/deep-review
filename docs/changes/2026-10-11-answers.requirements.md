# Product Requirements: Answers

Technical part: [2026-10-11-answers.design.md](2026-10-11-answers.design.md).

## Summary

A person answers a question the decision step asked, or accepts or
rejects a departure a fix made from a rule, with one command,
`deep-review answer`, after the run has written its report. The answer
goes on the run's ledger as a fact before anything is edited. On a run
that fixed, the engine then sends that finding alone back through a
fixer: the fixer makes the tree hold the option the person chose, in
place of the default the run applied, states the rule the person's
choice stands for where the repository states such rules, and the
checks run again; `deep-review commit` then commits that work on top of
the commits the run already made. On a run that only reviewed, the
answer is recorded and the continuation into the fix pass applies it
with the other fixes. Today an ask is answered by a default and nothing
can be said back to the engine: the recommended option, which differed
from the applied default in 17 of the 21 questions this repository's
runs asked, is lost unless a person does the work by hand, and nothing
records what the person decided.

This is the second item of the plan reoriented on 2026-10-10 and the
first element written against the vision note of 2026-10-11. It
implements principles 4, 7, 9 and 10 of that note: a question only a
person can answer is asked once, the answer comes later and fixes only
its finding, the answer becomes a rule, and the answer is a label.

## Problem

The decision step decides every ranked finding before any fixer runs:
`fix`, `leave`, or `ask`. An ask carries a question, two to four
options each with its cost and the rule a convention source would state
for it, the option recommended, and the option applied, which is the
one easiest to take back (decision step, R3, R4). The run never waits:
a fixer applies the default when it edits the code, and the report
lists the question as a checklist item for the author (R8). The
decision step left two things out on purpose (its Non-Goals): a memory
of answers, and an `answer` command that records the author's answer
and fixes that finding again.

What the runs since then show, read off this repository's own ledger on
2026-10-11:

| | |
|---|---|
| Runs with a decision step | 11 |
| Decisions | 243 |
| Questions asked | 21 |
| Questions whose default keeps the code | 17 |
| Questions whose default edits the code | 4 |
| Questions whose recommended option is not the applied one | 17 |
| Fixes that depart from a rule | 11 |

- **The recommended option is lost.** In 17 of 21 questions the decider
  recommended an option other than the default it applied. The default
  is the right thing to apply unasked, by R4 of the decision step; but
  there is no way to say "take the recommended one", so the question's
  answer is whatever the person does by hand after reading the report.
  In the one case so far where the author answered, RIPPLE-3 of the
  continuation gate (run `9b0f59a4`), the author rewrote the
  requirement by hand (`528aa8b`), and the engine knows nothing of it.
- **Nothing records the answer.** The overturn rate the decision step
  defined as a metric, the share of decisions an author reverses, is
  still unmeasurable: nothing records an answer, so no answer is a
  label (vision, principle 10).
- **The rule is not written.** Each option carries the rule a convention
  source would state for it, written so that the next review settles
  the question alone (decision step, R3; vision, principle 9). It is
  printed in the report and goes nowhere. A question the person answers
  by editing the code is asked again by the next review of a change
  that touches the same question.
- **A departure cannot be reviewed.** A fix that departs from a rule
  names the rule, its source and the reason, and amends what states the
  rule (decision step, R5). The vision gives the person three choices
  on a departure: accept, reject, or do nothing (principle 3). Only the
  third exists.
- **After `commit` the run is closed.** Every worktree check compares
  `HEAD` with the scope's head, and `deep-review commit` refuses a run
  whose `HEAD` is not the scope's head (`refuse` in
  `src/review/commit.ts`). Once the series is committed, `HEAD` is the
  series' last commit, so no worker can run on the run again. An answer
  that arrives after the commits, which is when a person reads a pull
  request, has no run to act on. The plan's third item, questions
  answered on the pull request, cannot exist without this.

What the questions were about matters for where the rule goes. Every
one of the 21 is a question about the engine's own behavior: which run
`commit` picks with no `--run`, whether a check's revision takes a file
the check created, whether the skills pass `--fresh`. The rule text of
each option is a sentence of product behavior, and the places the
decider looked are the change proposals under `docs/changes/` and the
docstrings beside the code, not `AGENTS.md`. The one answer given by
hand went into the proposal that states the behavior. The plan item
names "`AGENTS.md` or the file the survey found" as the rule's home;
that is the wrong default for this repository, and would be for a
library whose questions are about its own semantics. The rule belongs
where the repository states the behavior the question is about, and
which file that is takes judgment.

## Goals

- A person answers a question, or reviews a departure, with one command
  that needs nothing but the finding's id and the option's number as
  the report prints them, and the answer is on the ledger before any
  edit.
- An answer on a run that fixed is applied by one fixer to that finding
  alone: the tree comes to hold the chosen option, the rule is stated
  in the repository, the checks run again, and the work can be
  committed on top of the run's commits.
- An answer on a run that only reviewed is applied by the continuation
  into the fix pass, with no second review.
- Every answer, accepted departure and rejected departure is a recorded
  fact a later measurement can read as a label.
- The next review of the same question decides it from the rule the
  answer wrote, and does not ask again.
- An older engine still reads every ledger it could read before, and
  this engine reads every ledger written before it.

## Non-Goals

- **No free-text answer.** An answer is one of the options the ask
  gave, or accept or reject on a departure. An option the decider did
  not offer has no cost and no rule text written for it, and would need
  a decider's turn to get them; the person who wants it edits the code
  and the rule by hand (PD8). Revisit when answers show the need.
- **No answer to a `leave` or to a `fix` without a departure.** A leave
  cites a reason, and a person who disagrees with an `intended` leave
  disagrees with the rule it cites: the vision's answer is that the
  person changes the rule (principle 4), which a convention source edit
  does without the engine. A fix without a departure is the engine's
  own decision on a question the repository answers; overruling it is
  editing the code (PD9).
- **No re-fix on a tree that moved.** When `HEAD` is not at the run's
  head, the scope's or the last commit the engine made, the answer is
  recorded and the re-fix is refused with the rule text and where the
  decider looked, for the person to carry (R6). Reviewing a changed
  tree from the last run's verdicts is the plan's seventh item.
- **No repair in the answer pass.** The pass runs one fixer and the
  checks; a check that fails after it is reported, as the fix pass
  reports one its repair could not mend. A repair for an answer is
  built when a run shows the need (principle 11).
- **No change to the decider's rubric or output.** The ask's shape,
  `decisions.recorded@1`, is unchanged; where the rule goes is the
  fixer's judgment at answer time (PD3). The change the decision step's
  gate suggested, a `fix` whose approach makes no edit treated as a
  leave, is a rubric change that is measured before it lands and is not
  made here (PD10).
- **No pull request surface.** The command is the one surface; the
  plan's third item posts questions as review threads and reads replies
  as answers through this command.
- **No corpus work.** The answer event is what the plan's ninth item
  reads as a label; nothing here scores a rubric against it.
- **No `by` on the answer.** Who answered is not recorded; the pull
  request surface adds a version of the event with the account that
  replied, when it needs one.
- **No severity floor.** Deferred as before.
- **No Codex gate.** The element is accepted on Claude Code, as the fix
  pass and the continuation were (PD13).

## Requirements

- **R1: `deep-review answer` records one answer on the ledger.** The
  command takes `--finding <id>`, the finding's id as the report prints
  it, and one of `--option <n>`, the option's number as the report
  numbers it from 1, `--accept` or `--reject`; optionally `--note
  <text>`, `--run <id>`, `--record-only`, `--budget-usd <usd>`, `--roles
  <dir>` and `--repo <dir>`. It appends one `answer.recorded` event to
  the run, naming the finding, the answer and the note, before anything
  else happens. The event is appended under the run's lock, after the
  run is read again under it, as every writer of a run does.
- **R2: Which run.** With no `--run`, the run is the newest complete run
  of this worktree that was configured with the decision step, by its
  last event in the ledger; `--run` names another. A run that is
  active, blocked or abandoned, one of another worktree, one configured
  before the decision step, or one this engine cannot read is refused
  with the reason, exit 2; a run with no `--run` when none qualifies is
  refused naming `--run`. A finding the run's ranking does not hold is
  refused naming the run and the ids that can be answered on it.
- **R3: What can be answered.** `--option <n>` answers a finding decided
  `ask`, with `n` among its options; `--accept` and `--reject` answer a
  finding decided `fix` with a departure. Anything else is refused with
  the finding's decision and what it admits. A finding may be answered
  again; the last recorded answer stands, and an answer equal to the
  standing one is refused as already given. The chosen option may be
  the applied default: that confirms it, and the rule is still written
  (PD12).
- **R4: On a run that only reviewed, the continuation applies the
  answer.** A complete read-only run keeps its report; `answer` records
  the answer and says that `review --fix` applies it. The continuation
  (fix pass continuation, R1) then routes every answered finding to a
  fixer whatever its decision's default did, and that fixer is told the
  answer: for an option, the option and its rule text; for a rejected
  departure, that the fix follows the rule as stated; for an accepted
  one, nothing beyond the decision. The fixer makes the tree hold what
  the answer says and states the rule (R7). A continuation that finds
  nothing to fix (fix pass continuation, R5) counts an answered finding
  as one to fix. A continuation that does not qualify, because the
  change moved, creates a new run as today; the answers stay recorded
  on the old run, and the log says they do not carry.
- **R5: On a run that fixed, the answer pass applies the answer.** A
  complete fix run, continued or started with `--fix`, gets an answer
  pass unless `--record-only` is given: the engine appends one
  `answer.pass` event naming every answered finding whose standing
  answer no fixer has applied yet, which opens two phases, `answer` and
  `answer-checks`, and the report phase again; it then runs the run to
  its report in the foreground as `review` does, and exits as `review`
  exits. The `answer` phase launches one fixer, edit access, told every
  finding of the pass as a fixer is told a finding (decision step, R7)
  and, for each, what the run did with it before (the fixer's status,
  note and the files of its revision, or that no fixer saw it), and the
  answer. The fixer owns every file the run's revisions changed and may
  edit any other, as the repair worker may, claims nothing, snapshots
  after each finding so each answer is one revision and one commit, and
  returns the fixer's schema. The `answer-checks` phase runs the run's
  planned checks again, as the `checks` phase runs them after the
  fixes, and a check that fails is reported. A fixer that fails twice
  blocks the run with `worker-failed`, as the decider does, since an
  answer is the person's act and nothing else waits; the run budget
  blocks the phase before a launch as it blocks a reading phase. A
  later `answer` after the pass's report opens another pass.
- **R6: The pass needs the tree where the run left it.** Before the pass
  is opened, `HEAD` must be the run's head: the scope's head, or when
  `deep-review commit` made commits for the run, the last commit of the
  last series it made; and every file the run expects must hold what
  the run recorded last, compared as git would store it. Otherwise the
  pass is refused, exit 2, the answer stays recorded, and the message
  names what moved, the chosen option's rule text, and the places the
  decider looked, so the person can state the rule by hand; it says
  that a review of the changed tree is a new run, which does not carry
  the answer. A run whose spend reaches the run budget in force is
  refused before the pass, naming `--budget-usd`, as a continuation is.
  An interrupted pass is resumed by `review`, which resumes any active
  run; the answers recorded are then applied by the resumed pass.
- **R7: The rule is stated where the repository states such rules.**
  The fixer that applies an answer writes the rule the chosen option
  carries into the repository, choosing the place by what the
  repository already does: the document, comment or test that states
  the behavior the question is about, which the decision's `searched`
  list names, or a convention source the survey named that governs the
  files, amending an existing statement where one exists rather than
  adding a line beside it. A rejected departure restores what stated
  the rule, which the departing fix amended, and follows the rule. The
  file the rule went into is in the finding's `files`, so it is in the
  finding's revision and commit, and the commit message's body names
  the question and the answer. An accepted departure writes nothing:
  the departing fix amended the rule's statement already.
- **R8: `deep-review commit` commits an answer pass on top of the run's
  commits.** A run whose revisions were committed and that then gained
  revisions in an answer pass is committable again: `commit` builds one
  commit per uncommitted revision, in ledger order, from the last
  commit it made for the run, refusing a `HEAD` that is not that
  commit, and records a second `commits.created`. In worktree mode the
  captured change is committed by the first series only. With no
  `--run`, `commit` picks the run that finished last among those with
  revisions no commit holds. A run never committed is committed as
  today.
- **R9: The ledger records answers and passes, and every older ledger
  still reads.** Two kinds: `answer.recorded@1`, the answer; and
  `answer.pass@1`, the pass and the findings it applies. Two phases,
  `answer` and `answer-checks`, after `repair-checks` and before
  `report`, skipped at every configuration and opened only by an
  `answer.pass`; the kinds that carry a phase gain a version that can
  name them. The fold holds every answer and every pass, the second
  report takes the first's place and the first stays beside it, as a
  continuation keeps its read-only report, and `commits` becomes a
  list. Every committed golden fixture and every recorded run of the
  replay corpus still opens and folds, and a new golden fixture holds
  an answered run.
- **R10: The report and `status` show the answers and how to give one.**
  Under Decisions, each question's checklist item is checked once
  answered, with the option chosen, when, and whether and by which pass
  it was applied; each departure says accepted or rejected, when. Each
  unanswered question and each unreviewed departure ends with the
  `answer` command that answers it, finding id and the options'
  numbers filled in, so a reader needs nothing else to answer. The
  header says how many answers the run holds and, after a pass, when
  the last pass ran and where the report before it is. Fixes shows the
  answer pass's outcome for each finding it worked, the Checks table
  gains the pass's column, and the patch series holds the pass's
  revisions after the run's. `status` prints the answers' counts and
  the passes, and `--json` carries them.
- **R11: The auditor leaves the role prompts.** The `auditor` role, its
  fragments `auditor-brief.md` and `step3-verdicts.md`, and the unused
  `answer` role of the manifest, whose fragments are the fixer's, are
  removed, since the audit they served was set aside and answers take
  its place; the fixer's prompt no longer promises a later adversarial
  pass over its defers. Each is its own commit, and the roles digest
  changes, so an active run resumes only with `--roles <dir>`.
- **R12: The skills and the README say it.** Both skill texts say that
  the report's Decisions section lists the questions and departures
  with the command that answers each, how to run it when the user
  answers one, what its exit codes mean, and that after answers on a
  read-only run the same command with `--fix` applies them. The skill
  texts change in their own commit. `README.md` gains a section on
  answers and points at this proposal.
- **R13: The gate.** On this repository, on Claude Code, with no hand on
  the runs: the element's own change is reviewed read-only; one
  question is answered before `--fix` continues the run, choosing the
  recommended option when it is not the default (R4); after the fix
  pass and `deep-review commit`, another question is answered, or a
  departure rejected, and the answer pass runs and is committed on top
  (R5, R8); `npm run check` and `npm run verify` pass at the head. When
  the change's review asks no question, the read-only path is taken on
  the newest finished run of this worktree that asked one, and the
  pass path on a departure. The design's Verification records both
  reports, the pass's spend and workers, where each rule went, and the
  measurement of the first metric.

## Metrics

- **Asked again.** After an answer's rule is in the tree, the decider,
  run again over the same recorded findings on that tree with the
  experiment harness the decision step measured with (its R13), decides
  the answered finding without asking: target 0 of the answered
  findings asked again, over two samples. This is the measurement of
  principle 4's "not again".
- **The cost of an answer.** The answer pass's spend and workers, from
  the report's Statistics, against the read-only review's: target one
  fixer and the checks, under 5 USD on this repository.
- **The overturn rate**, defined by the decision step and unmeasurable
  until now: the share of asks whose answer is not the applied default
  and of departures rejected, over all asks and departures of a run,
  read from the ledger. Recorded from this element on; no target yet.

## Product Decisions

- **PD1: The answer is a fact first; the re-fix needs the tree.** An
  answer is recorded whatever the tree holds, since it is the person's
  decision and the corpus's label (principle 10), and the re-fix is
  refused when the tree moved (R6). Refusing the answer itself when the
  tree moved was rejected: it would lose the label and make the person
  answer again later.
- **PD2: One command for questions and departures.** The vision treats
  an answer and a reviewed departure alike as what becomes a rule and a
  label (principles 3, 9, 10), and the re-fix is the same work: a
  fixer told what the run did and what the person decided. A second
  command for departures was rejected as two names for one act.
- **PD3: The fixer places the rule; the engine does not.** The plan item
  named `AGENTS.md` or the file the survey found. Every question this
  repository's runs asked was about the engine's behavior, its rule
  text a sentence of product behavior, and the one answer given by hand
  went into the change proposal that states the behavior; the decider's
  own `searched` list names where such statements live. Writing the
  rule mechanically into a convention source was rejected: inserting a
  sentence into prose at the right place is a judgment, and a rule
  beside the wrong text is noise the next decider does not find. The
  fixer that applies the answer reads the places the decision searched
  and the convention sources, and amends the one that states the
  behavior (R7). Asking the decider to name the place at decision time
  was rejected for now: it changes the ask's shape and the decider's
  rubric, which was measured; the gate's reading of where each rule
  went says whether that is needed.
- **PD4: A read-only run's answers ride the continuation.** A pass on a
  read-only run would need the fix pass's pins, the checks and a
  survey, for one finding; the continuation already routes every
  finding by its decision and asks the surveyor for the checks once.
  So an answered finding routes to a fixer under the continuation and
  the fixer is told the answer (R4). The person's step is then
  `answer`, then `review --fix`, which the skill says.
- **PD5: One fixer for every unapplied answer, with no claims.** The
  pass runs alone: no other editor is in the tree, so the claims that
  keep fixers apart serve nothing, and one worker over two or three
  findings is one worker. One worker per answer was rejected as more
  launches for the same edits; running the pass inside the fixes
  phase as a third round was rejected because the claims, the rounds
  and the second-round plan are built for two rounds and the pass
  needs none of them.
- **PD6: Confirming the default still writes the rule.** An answer that
  chooses the applied option changes no code, but the question is asked
  again by the next review unless the rule is stated (principle 9), so
  a fixer runs for it. Writing the rule mechanically for that case was
  rejected with PD3.
- **PD7: After `commit`, the run's head is its last commit.** The
  worktree check and `commit` compare `HEAD` with the scope's head
  today, which closes a committed run. The run's head becomes the last
  commit the engine made for it, when it made one (R6, R8); the
  expected files are unchanged, since the commits are built from the
  same frozen bytes. Reopening the run by rewinding `HEAD` was rejected
  as a hand on the tree; copying the run was rejected by PD1 of the
  continuation.
- **PD8: Options only.** A free-text answer would carry no cost and no
  rule text and would need a decider's turn to get them; the options
  are what the person can decide from the question alone (principle 6).
  A person who wants another option edits by hand; the report says so.
- **PD9: A leave and an undeparted fix are not answerable.** See
  Non-Goals. The population to overrule them is the audit's, which the
  plan set aside at 0 in seven runs; reopen with it.
- **PD10: The rubric does not change here.** The plan item bundles a
  rubric change, a `fix` with no edit read as a leave. The decision
  step's rule is that a rubric change is measured before it lands, and
  its gate found the case twice in two pytest runs and never since. It
  is its own small proposal, measured on the replay corpus, and not
  mixed into an engine change whose gate reads something else.
- **PD11: `answer` records and then runs; `--record-only` defers.** A
  command that only records, with `review` running the pass, was
  rejected: the pass would have to be opened at record time to make
  the run resumable, and a run left open that way would be resumed by
  the next `review` of another change in the worktree, which ignores
  scope flags for an active run. So `answer` opens the pass only when
  it is about to run it, and `--record-only` leaves the run complete
  for the next answer. An interrupted pass is resumed by `review`, as
  any active run is.
- **PD12: The chosen option may be the default.** See PD6. Refusing it
  as a no-op was rejected: it is an answer, and a label.
- **PD13: The gate runs on Claude Code only.** As for the continuation;
  the plan's tenth item is the cycle on Codex.

## Against the vision note

Read against `docs/2026-10-11-vision.md`:

- Principle 2, record before action: the answer is on the ledger before
  the fixer launches (R1), and the pass before the phases open (R5).
- Principle 4, asked once: the rule is written with the answer (R7),
  and the first metric measures that it is not asked again.
- Principle 5 and 6, what reaches the person: the report's checklist
  gains the command that answers each question, so a person answers
  from the question alone (R10); nothing more is added to read.
- Principle 7, nothing waits: the pass fixes the answered findings only
  (R5), on a run that already reached its report; no question blocks.
- Principle 9, rules grow from answers: deep-review writes the rule and
  the person confirms it in the commit (R7, PD3); a reviewed departure
  changes the rule or restores it (R7).
- Principle 10, answers are labels: `answer.recorded` is the label (R9,
  PD1).
- Principle 12, a real run is the gate (R13).

One departure, named: principle 9 does not permit a rule that only a
person can write by hand, and R6 leaves the rule to the person when the
tree moved past the run. The reason is that a fixer on a tree the run
does not know would edit without the expected tree the record rests on
(principle 1); the plan's seventh item, review of a changed tree from
the last run's verdicts, is where the rule follows the change. Until
then the refusal prints the rule text and where it belongs.

## Risks

- Risk: the fixer states the rule in the wrong place, and the next
  decider does not find it. Accepted for now: the file is in the
  commit the person confirms, the report names it, and the first
  metric measures the miss; PD3 names the change if the gate shows it.
- Risk: rules accumulate. Each answered question adds a sentence to a
  document; over many runs the convention sources and proposals grow
  with narrow rules. Accepted: the fixer is told to amend an existing
  statement rather than add beside it (R7), and the vision takes the
  growth as the mechanism by which the engine asks less.
- Risk: the answer pass's fixer, owning every revised file and free to
  edit any other, undoes a sibling fix while applying an answer.
  Accepted: it is told what each fixer did and each finding is one
  revision the person reads; the checks run after it.
- Risk: a person edits the tree by hand between the commit and the
  answer, and the pass is refused for drift. Accepted: the refusal
  names the files and the rule text; the answer stays recorded.
- Risk: the run's head moving with its commits reaches every reader of
  the scope's head. Mitigated by one function the drift check and
  `commit` both call; the base state of a path outside the expected
  tree stays the scope's head's, since the commits change only expected
  paths.
- Risk: two reducers now move phases out of `skipped` or `completed`,
  the continuation's pin and the answer pass. Accepted: each is one
  event that says what it reopens, and `phaseStarted` keeps its rule.
- Risk: the roles digest changes with R11, so every active run must be
  resumed with `--roles <dir>` or started again; a finished read-only
  run under the old roles is continued only with `--roles` too (fix
  pass continuation, PD8). Accepted as at every prompt change.
- Risk: the gate change asks no question. Then R13's read-only path
  runs on the newest finished run of the worktree that asked one, and
  the pass path on a departure, which every dogfood run so far had.
- Risk: cost. One strong fixer and the checks per answer pass, under
  the fixer's 8 USD cap; measured at the gate.
