# Implementation plan: the brief of a run

This is the plan of the work for the [requirements](2026-10-20-run-brief.requirements.md) and the [design](2026-10-20-run-brief.design.md). It stays in the pull request while the work continues, and the commit that records the verification deletes it. It is not a part of the proposal, and it records no decision. The proposal records the decisions.

Each step names each file that it changes and the commands that prove it. The steps run in order, and the checks of a step pass before the next step starts. `npm run check` passes at each commit.

`npm run verify` passes at each head that is pushed, as `AGENTS.md` says, and CI runs it too. Thus each batch of commits that goes to origin ends with `npm run build`, and with a `chore(dist)` commit when `dist/` changed.

The proposal can change during the work. If the code needs a different design, a commit of its own amends the proposal before the code commit. Thus the pull request shows each change of the proposal beside the code that needed it.

- The branch is `feat/run-brief`, in its own worktree, so the main checkout stays on `main`. The branch holds the proposal, this plan and the implementation. Its name was set before the first push, because a rename of a pushed branch closes its pull request.

## 2. The record and the fold (R3, R18)

Files:

- `src/checkpoint/events.ts`: `changeReadingSchema`, with the fields and the rules of the table "The triage's account of the change" of the design. `candidatesRecordedV2`, which is version 1 with `change`, refused on a phase other than the triage and needed on the triage. - `test/fixtures/checkpoints/schema-1-14`: new, from `npm run golden`.

Tests:

It refuses what the normalization never writes: a condition that does not hold but has a sentence or files, and a null `why` with sources. Version 1 folds to `change: null`, and version 2 folds to the triage's account.
- `test/checkpoint/golden.test.ts`: passes with the new fixture, and each older fixture still opens and folds.

## 12. The self-review and the build

- A review of the whole diff against the proposal and against the checklist of the self-review. Each finding gets a test that fails first, then its fix.
- An independent review by a fresh agent, which reads the proposal, this plan and the diff. Its findings get the same treatment.
- `npm run build`, then `npm run check`, `npm run verify` and `npm run resume-test`.

```sh
git commit -m "chore(dist): Rebuild the engine with the brief of a run"
```

## 13. The gate (R19)

Each paid run waits for the word of the author.

- The engine of the gate is a copy of `dist/claude` at the head. It runs from outside the worktree of the gate, because the build check rewrites `dist/`.
- The run: `review --runtime claude --branch --fix`, with the settings of the repository.
- A read-only run on Codex shows that the triage of that runtime writes the account too.
- The author reads the brief of the gate run, answers each question from its block alone, and judges the core.
- `deep-review commit`, then typecheck and lint at each commit alone, and an audit of the ledger.
- The fixes of the gate go in a pull request stacked on this one, which merges into this branch by a fast-forward.
